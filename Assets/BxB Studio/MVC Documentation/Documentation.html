Getting started
This manual documents Multiversal Vehicle Controller from installation through production use. It covers the Settings Panel, editor tools, scene components, runtime behaviour, twenty practical tutorials, diagnostics, upgrades, terminology, and units.
Multiversal Vehicle Controller, abbreviated MVC, is a [https://unity.com](Unity) toolkit for building controllable and AI-driven vehicles. Read the manual in order when creating a first project, or use the navigation and search as a field reference. A Pro badge immediately to the right of a section title means the complete section requires MVC Pro. A Pro badge beside a subsection title applies only to that named field, component, or workflow, with its exact scope explained directly below. If a suitable title is unavailable, the badge follows the associated content instead. Unmarked content describes the Community-compatible foundation unless a nearby note states otherwise.
This manual describes visual workflows and user-facing behaviour. For public types, members, runtime scripting, and extension code, use the [API.html](API Scripting Reference). Preserve a source-control checkpoint before installation, upgrades, imports, or repair operations.
Recommended order: [#getting-started-how-to-install](Install), [#setup-wizard](run the Setup Wizard), optionally [#custom-wheel-colliders](import a custom wheel integration), [#settings-panel](review project settings), [#tutorials-setup-and-create-a-vehicle](build a first vehicle), then use [#components-and-behaviours](component reference) and [#troubleshooting--maintenance--and-reference](troubleshooting) as needed.
How to install
Install MVC into a project that has finished importing and compiling. For an existing project, commit or back up the working state first and record the installed MVC edition and version.
Install MVC from Unity's Package Manager after acquiring the package from the Unity Asset Store. Open `Window > Package Management > Package Manager`, select `My Assets`, locate Multiversal Vehicle Controller, and import the current package into the project. Existing projects should create a source-control checkpoint or project backup before replacing an earlier MVC release.
If you received an explicit `.unitypackage` build instead, use `Assets > Import Package > Custom Package...`, select the downloaded file, and allow Unity to decompress and compile the package before changing scenes or entering Play Mode.
In the Unity Package Importer, keep the MVC package content selected and click `Import`. Wait until Unity finishes dependency resolution and script compilation. Resolve the first Console error before attempting setup; later errors can be consequences of an incomplete import or a missing dependency.
The installation workflow can request required packages or project changes. Review and accept the requests that match the project. If Unity asks to restart or apply a project-wide setting, save current work before accepting. If the installation window does not reopen after a restart, use the MVC installation command from `Tools > Multiversal Vehicle Controller`.
Optional physics products are installed separately from MVC. Finish MVC installation and the Setup Wizard first, then follow [#custom-wheel-colliders](Custom wheel colliders) to import a compatible adapter and change the project-wide Physics System.
Do not keep an older MVC copy under `Assets` while also installing the current release as a package. Duplicate scripts and assembly definitions can produce ambiguous types, missing menus, or inconsistent serialization.
Setup wizard
The Setup Wizard establishes the project-wide prerequisites that MVC components expect. Run it after a clean installation and review it again when changing render pipeline, input backend, or MVC edition.
After installation succeeds, open the `Setup Wizard` if it does not appear automatically, then click `Let's get started`.
The `Configurations` panel summarizes the choices that affect how MVC creates and initializes project content. Choose each value deliberately; global choices must agree with the packages and project settings already installed.
  • Render Pipeline: Select the [https://docs.unity3d.com/Manual/render-pipelines.html](render pipeline) already configured by the project. MVC can detect common pipelines, but changing this value does not create or assign the required Unity pipeline asset. Supported choices are Standard (Built-in RP ), `Universal Render Pipeline`, `High Definition Render Pipeline`, and `Custom Render Pipeline`.
  • Physics: The Setup Wizard establishes `Wheel Collider`, Unity's built-in wheel implementation, as the initial project baseline. Install and select optional integrations afterward through [#custom-wheel-colliders](the custom wheel collider workflow). [#settings-panel-general-physics-system](Read more...)
  • Agent Type: The agent type that will be used by the toolkit's AI systems.
    • Using the built-in `Humanoid` agent settings is not recommended. You'll have to create your own agent type by using the button. You can also click on `Show Recommended Agent Settings` to see the best recommended you can use when creating a new agent type.
  • Vehicles Layer: The layer that MVC uses to regroup its GameObjects.
  • Wheels Layer: A layer used to regroup any available wheels GameObjects.
    • `Vehicles Layer` and `Wheels Layer` must be assigned to a layer different than the built-in `Default` layer.
    `Vehicles Layer` and `Wheels Layer` values cannot match.
  • Walkable Mask: A layer mask for AI walkable objects.
  • Non-Walkable Mask: A layer mask for AI non-walkable areas, objects and obstacles.
    • `Walkable Mask` and `Non-Walkable Mask` cannot have common layers, keep in mind that the `Vehicles Layer` and `Wheels Layer` cannot added to the mentioned masks as this can cause runtime issues.
    `Non-Walkable Mask` can be empty, unlike `Walkable Mask` which has to have at least one layer added including the built-in `Default` layer.
    You can click on `Add Recommended Layers` to add and setup layers for your project automatically.
  • Runtime Units: To know more about this field, [#settings-panel-general-runtime-units](read this section...)
  • Editor Units: Just as the Runtime units, the Editor Units are the same, except that the expressed values appear in the MVC component inspectors and within the [#settings-panel](Settings panel).
  • Inputs System: The Inputs System is a system that manages the user's inputs like a keyboard keys or a joystick's. The MVC uses two options:
    • Inputs Manager: BxB Studio's input workflow built on Unity's Input System, with one editor for keyboard and gamepad bindings.
    • Unity Legacy Input System: Uses the project's existing named axes from Unity's legacy input settings.
  • Audio Folder Path: Is the path the MVC should save audio files and sound effects, the folder should be inside a `Resources` folder, so the MVC can load them at runtime.
    • Click on Use Suggested Path to use the recommended path suggested by the toolkit.
After assigning all of the needed fields, click `Next`. A confirmation message will appear, click `Yes` to proceed with the setup process.
You might be prompted to import the [#sample-and-demo-packages](Getting Started Demo Packages) before starting the setup process.
Running the Setup Wizard again can restore Unity Wheel Collider as the physics baseline. If the project uses an optional integration, reopen General settings afterward and confirm the intended Physics System before testing vehicles.
Once the import process is done, a success message should appear. To close the panel, click `Open Settings` to show the [#settings-panel](Settings panel).

Custom wheel collidersPro
Replace Unity's built-in WheelCollider backend with an installed MVC-compatible integration when the project needs a different tire model or wheel-contact implementation.
Selecting any external wheel-physics integration requires MVC Pro. Pacejka Wheel Collider is a separately purchased optional product; Unity Wheel Collider remains the bundled Community and Pro default.
A custom wheel collider is more than a component placed beside an MVC wheel. MVC sends wheel geometry, suspension, friction, torque, braking, steering, and contact requests through a backend contract. The imported package must therefore include an MVC integration that translates those requests into the custom simulation and returns compatible wheel state. Installing an unrelated wheel asset without that adapter does not make it selectable in MVC.
Unity Wheel Collider remains the bundled default and the safe fallback. External integrations are discovered from loaded assemblies and appear in `Tools > Multiversal Vehicle Controller > Settings > Open Panel > General > Physics System` only after their runtime requirements and MVC adapter are available.
Changing the Physics System changes the physical baseline for every MVC vehicle in the project. Create a source-control checkpoint, record a repeatable test result, and switch integrations outside Play Mode.
Recommended product: [https://u3d.as/3Y2F](Get Pacejka Wheel Collider on the Unity Asset Store) for the ready-made BxB Studio integration described below.
Why Pacejka Wheel Collider
Pacejka Wheel Collider is the first-party optional path for teams that want to move beyond Unity's standard slip curve while retaining MVC's vehicle, drivetrain, input, damage, ground, audio, visual, camera, and tooling workflows. Its MVC sample supplies the adapter; MVC then continues to own the vehicle-facing configuration while the Pacejka backend performs wheel simulation.
The main reason to choose it is control over tire-force behavior. A Pacejka Magic Formula curve represents the relationship between tire slip and generated force with B, C, D, and E coefficients. MVC can fit a useful starting curve from an existing WheelCollider-style tire definition, allowing a vehicle to migrate before advanced coefficients are authored manually.
The integration also reports that it applies camber, caster, and toe through the physical collider. Those suspension adjustments are visual-only with Unity Wheel Colliders, but they can participate in the Pacejka simulation. This makes the integration a strong fit for projects where alignment setup and progressive tire response are part of the driving design rather than presentation alone.

Import the MVC integration
Complete MVC's [#setup-wizard](Setup Wizard) before selecting an optional backend. The wizard establishes the project settings and Unity Wheel Collider baseline. Import and select the custom integration afterward so the wizard does not replace the intended physics selection.
For the MVC release covered by this manual, use Pacejka Wheel Collider `2.0.1-beta` or newer. Package requirements can change independently, so review the current Unity Asset Store listing, package manifest, and release notes before purchasing or upgrading.
  1. Commit or back up the complete Unity project while its current MVC vehicle opens, compiles, and drives correctly.
  2. Acquire [https://u3d.as/3Y2F](Pacejka Wheel Collider) from the Unity Asset Store.
  3. Open `Window > Package Management > Package Manager`, select `My Assets`, locate Pacejka Wheel Collider, and download or import the compatible release.
  4. Allow Unity to resolve the package dependencies and finish script compilation. Stop and resolve the first Console error before importing the MVC adapter.
  5. Select the installed `Pacejka Wheel Collider` package in Package Manager and open its `Samples` list.
  6. Import the sample named `MVC Integration`. This adds the adapter assembly and backend scripts that connect the Pacejka simulation to MVC.
  7. Wait for compilation again. The integration assembly requires an installed MVC edition symbol and the package references declared by the sample; do not remove its assembly-definition references.
  8. Open `Tools > Multiversal Vehicle Controller > Settings > Open Panel`, select `General`, and find `Physics System`.
  9. Select `Pacejka Wheel Collider`. MVC saves the integration's stable name in the Settings asset and creates its typed global settings.
  10. Save the project and reopen the Settings Panel to confirm the Pacejka selection remains active before entering Play Mode.
When Pacejka is not yet available, MVC Pro displays an add button beside Physics System. It opens the same product page used by this guide. After the package and MVC Integration sample compile successfully, the installed integration appears in the selector.
Do not copy the sample scripts into an arbitrary assembly, rename the integration identifier, or manually add Pacejka authoring colliders under every MVC wheel. The adapter creates and owns the required per-wheel backend objects.
Migrate and retune
Treat the first Pacejka run as a migration test, not as a direct quality comparison. MVC preserves vehicle-facing settings where possible, but an integration can interpret friction, anti-sway loads, contact, suspension alignment, and low-speed behavior differently. Comparing two backends while also changing mass, power, tires, or the fixed timestep hides the cause of every difference.
Establish the Unity baseline
Before switching, run the same launch, straight-line braking, constant-radius corner, curb crossing, slope start, reverse, and recovery maneuvers with Unity Wheel Collider. Record speed, stopping point, visible suspension movement, wheel contact, forward and lateral slip, and whether ABS, TCS, ESP, or counter-steer activates. Preserve the tire compound assigned to each wheel.
Start from fitted tire curves
Open `Settings > Tire Compounds` after the Pacejka integration is discovered. Each acceleration, brake, and sideways Pacejka curve can use `Fit From Slip Curve` or `Manual` as its source. Begin with the fitted source so MVC derives valid coefficients from the existing WheelCollider-style extremum and asymptote curve.
Use `Refresh Fits` after deliberately changing the source slip curves. The automatic fit is a migration aid and a practical starting point; it is not certified real-world tire data. Repeat the same test route and confirm that the new force curve solves the intended handling problem before editing coefficients.
Use manual coefficients carefully
Switch a curve to `Manual` only when the project needs direct Magic Formula control. In the exposed formula, B primarily affects stiffness, C shapes the curve, D controls its peak, and E changes curvature around and beyond the peak. Use the preview, modify one value at a time, and test acceleration, braking, and cornering separately.
Review integration-owned settings
Unity's `Vehicle Sub Steps` fields are replaced by the active integration's own settings when Pacejka is selected. Pacejka exposes friction-solver iterations. Higher iteration counts can spend more work resolving friction, but they should be increased only after a repeatable test demonstrates a need and target-hardware profiling confirms the cost is acceptable.
Validate the complete vehicle
  • Every wheel is created, grounded on the expected surfaces, and reports stable RPM and slip.
  • Wheel radius, mass, suspension length, spring target, stiffness, damping, and resting travel remain plausible.
  • Camber, caster, and toe now produce the intended physical response as well as the intended visual pose.
  • Acceleration, braking, steering, reverse, handbrake, differentials, trailers, and low-speed starts still work.
  • Tire compounds respond consistently across mapped grounds, wetness, temperature, wear, and damage used by the project.
  • ABS, TCS, stability, anti-sway, counter-steer, AI braking, and recovery are retested rather than assumed equivalent.
  • Wheel models, marks, particles, rolling audio, skid audio, and the Vehicle Profiler agree with physical contact.
  • Editor and target-platform profiling remain inside the vehicle-count and wheel-count budgets.
The Pacejka integration requests Rigidbody interpolation when required, and MVC enables it when the vehicle has none. Record that project behavior when comparing presentation or investigating visible wheel jitter.

Safe rollback
  1. Exit Play Mode and save a copy of the current MVC Settings asset and tuned tire data.
  2. Open General settings and select `Unity Wheel Collider` while the Pacejka integration is still installed.
  3. Save, reopen the panel, and verify Unity Wheel Collider remains selected.
  4. Run the Unity baseline scene and restore any backend-specific tire, alignment, stability, or Rigidbody choices required by that baseline.
  5. Remove the imported `MVC Integration` sample and Pacejka package only after no project assembly, prefab, or script depends on them.
  6. Allow Unity to compile and perform one final Editor and target-platform validation.
MVC keeps typed settings for integrations while switching between them, so returning to an installed integration can restore its previously serialized global values. Do not treat that convenience as a substitute for exported presets, source control, or a project backup.
Integrate another backend
A third-party or project-owned wheel system can participate in the same selector when it supplies an MVC adapter. Keep that adapter in a project-owned runtime assembly referencing MVC and the wheel package, with editor-only helpers in a separate editor assembly.
Implement `IVehiclePhysicsIntegration` on a non-abstract class with a public parameterless constructor. Give it a stable `Name` that will never change after serialization, a user-facing `DisplayName`, a diagnostic `Version`, an accurate `IsAvailable` result, and capabilities that describe the backend's friction, interpolation, anti-sway, braking, and free-wheel behavior. Return typed global settings and a new `VehicleWheelColliderBase` implementation from the factory methods.
The wheel backend must create and destroy its owned simulation objects, accept MVC's backend-neutral wheel configuration and friction state, apply torque, braking, and steering inputs, and report contact, pose, RPM, angular velocity, peak slip, and stiffness. The per-step path must remain allocation-free. MVC discovers qualifying integrations automatically; a manual registry edit is not required.
Do not reuse another integration's serialized `Name`, change a released name, report unsupported capabilities, or return a backend whose contact and slip units violate the MVC contract. These mistakes can silently load the wrong settings or destabilize assists and telemetry.
Use the [API.html](API Scripting Reference) for `IVehiclePhysicsIntegration`, `VehiclePhysicsIntegrationCapabilities`, `VehiclePhysicsIntegrationSettings`, `VehicleWheelColliderBase`, `VehicleWheelColliderConfig`, `VehicleWheelFrictionState`, and `VehicleWheelHit`. Validate a custom adapter with the same migration, rollback, and target-platform tests described for Pacejka.

Physics SystemPro
Selecting an external wheel-physics integration requires MVC Pro. Unity Wheel Collider remains the bundled Community and Pro default.
Physics System selects the installed integration that simulates every MVC wheel in the project. MVC discovers compatible integrations from loaded assemblies and stores the selection by its stable integration name, so the available list reflects packages that actually compile in this project.
  • `Unity Wheel Collider`: The bundled default and fallback. It uses Unity [https://docs.unity3d.com/Manual/class-WheelCollider.html](Wheel Colliders) for wheel contact, suspension, friction, and torque behavior.
  • `Pacejka Wheel Collider`: An optional, separately purchased integration using Pacejka Magic Formula tire curves. Import the product's `MVC Integration` sample before selecting it. [#custom-wheel-colliders](Installation and migration guide...)
  • `Other integrations`: Any compatible package can appear here when it implements MVC's physics integration contract, compiles successfully, and reports that its runtime requirements are available.
An unavailable entry cannot be selected. Resolve its package requirements and compiler errors first. MVC Pro also shows an add button while Pacejka Wheel Collider is absent; the button opens its Unity Asset Store listing.
The selector is disabled in Play Mode. Changing integrations is a project-wide migration and requires suspension, tires, stability assists, contact, wheel visuals, and target-platform performance to be revalidated.
Sub Steps
`Vehicle Sub Steps` belongs to the Unity Wheel Collider integration. During each [https://docs.unity3d.com/ScriptReference/MonoBehaviour.FixedUpdate.html](Fixed Update), MVC blends between the configured minimum and maximum using the vehicle handling rate. Additional sub-step work can improve resolution or stability while increasing physics cost.
When another integration is selected, MVC replaces the Unity sub-step controls with that integration's serialized settings. Pacejka Wheel Collider, for example, exposes friction-solver iterations. Tune and profile each backend through its own settings instead of carrying Unity's values across by name.
Steering Method
The steering method determines how input becomes steer angles at the wheels. MVC provides the following options:
  • `Simple`: A direct steering behavior based primarily on player or AI steering input.
  • `Dynamic`: A complex steering behaviour dedicated for a better anti-slip behaviour on higher speeds.
  • `Ackermann`: Is a geometry method commonly used in the Automotive industry to improve handling at lower and higher speeds. [https://en.wikipedia.org/wiki/Ackermann_steering_geometry](Read more...)
Transmission
Transmission behavior determines how the active gear is selected while the vehicle is driven. MVC provides the following modes:
  • `Automatic`: As the name suggests, Automatic is an automated behaviour of a certain system, in this case and while the Unity Editor is in Play mode, the user will just have to move the vehicle freely and the its transmission will shift its gears without a single input.
  • `Manual`: The driver selects gears through the configured shift and clutch inputs instead of automatic shift logic.
Wheel Renderer Refresh
This controls how the wheels rotation angles should be calculated.
  • `Accurate`: Calculates the wheels rotation angles precisely.
  • `Approximate`: Gives the wheels rotation angles approximate values.

Start Engines at Awake
Once the Unity Editor enters play mode, all of the vehicles engines will start up and they'll be controllable, once the Unity Editor enters play mode. Note that this feature is not available for `AI vehicle`s.
In case `Start Engines At Awake` is disabled, the player will be required to turn on his vehicle engine manually using the [#settings-panel-player-inputs-turn-on-off-engine](Turn On/Off Engine) input.

Fuel/Battery SystemPro
Fuel and battery capacity, consumption, depletion, refill, and recharge simulation require MVC Pro.
Enables fuel or battery capacity and consumption while an eligible vehicle operates.
Engine Stall
Engine Stall allows an eligible manual-transmission combustion engine to stop when the clutch is released into excessive load at insufficient RPM. Validate normal starts and deliberate stalls after configuring the clutch, first gear, engine torque, and vehicle mass.
This feature is not available for EVs or vehicles with automatic gearboxes.
Gear Limiter (First Gear/Reverse)
Gear limiter is a feature that prevents an Engine to Over-Rev or Under-Rev by adding brake/motor torque to the wheels, disabling this features (for the first/reverse gear only) will lead for the car stop automatically when not pressing the fuel pedal, but in any case, the engine RPM won't pass the engine's [#settings-panel-engines-and-chargers-engine-preset-redline-rpm](Redline RPM).
Burnouts For Auto Transmission
For vehicles with Automatic `Gearboxes`, enabling this allows the player to do [https://en.wikipedia.org/wiki/Burnout_(vehicle)](Tire Burnouts). In reality most car manufacturers that make automatic gearboxes don't allow drivers to do such stunts, burnouts are kind of exclusive to vehicles with Manual `Gearboxes`, since drivers have control over the [https://en.wikipedia.org/wiki/Clutch](Clutch) through the `Clutch Pedal`.

Tags & Layers
This section is dedicated to arranging the objects used by the toolkit for a better workflow.
Vehicles Layer
The Unity Editor layer used by vehicles using the toolkit, as well as some components like the `Vehicle Manager`, `Vehicle UI Controller`, `Vehicle Follower` and more...
Wheels Layer
A Unity Editor layer used for vehicle wheel models/renderers.
Game Controller Tag
The tag used by the Vehicle Manager component, the used tag makes finding the mentioned component much faster by other MVC components.
Player Tag
A GameObject tag assigned to vehicles without an `AI controller`.
Artificial Intelligence (AI)Pro
These settings provide common path, steering, recovery, sensing, and obstacle behavior for vehicles using MVC Pro AI control. Individual AI behaviors and path followers can add local configuration.
Agent Type
The preferred Unity [https://docs.unity3d.com/ScriptReference/AI.NavMeshAgent.html](AI Agent) for baking `AI Surface`s within the `Vehicle Manager` inspector. You can edit the currently used agent by clicking the button on the right side of the mentioned parameter. You can also show the recommended settings if you're willing to create a new agent, as using the default `Humanoid` agent settings is not recommended.
Smooth Steering
Smooth Steering interpolates the AI Controller's calculated steering target instead of applying it immediately, producing a less abrupt wheel response.
Steer Intensity
Refers to the steering speed intensity. Higher values cause a more responsive behaviour of the wheels.
Vehicle Path Distance
The required distance between an AI vehicle and a path point for the `AI Controller` to switch his focus on the next point of the `AI Path`.
The `Vehicle Path Distance` has two modes:
  • `Dynamic`: In this mode, the `Distance` value is an interval that has a `Minimum` and a `Maximum` for certain speeds.
    • `Min`: The vehicle to path point distance at 0 `Kilometres Per Hour (km/h)` / 0 `Miles Per Hour (mph)`.
    • `Max`: The vehicle to path point distance at 100 `Kilometres Per Hour (km/h)` / 62 `Miles Per Hour (mph)`.
  • `Fixed`: Where the `Distance` will be a fixed value without any ranges unlike the `Dynamic` mode.
Path Point Spacing
The distance between each `AI Path` point.
Reverse Timeout
The time an AI vehicle must remain unable to advance before its recovery behavior engages reverse.
Reverse Time Span
The amount of time it takes `AI Vehicle`s to disengage the `Reverse` gear.
Agent Refresh Timeout
A time span for AI agents to refresh their destination path.
Path Avoidance Curve
A smoothness curve for `AI Path` components used to avoid obstacles. The linear the curve is, the sharper `AI Path`s avoid obstacles.
The `Path Avoidance Curve` limits cannot exceed `0` and `1` on both axes, `Time (X)` and `Value (Y)`, otherwise the curve will be stretched or clamped automatically at Runtime which is not recommended.
Obstacle Detection
The following parameters control AI obstacle detection and avoidance.
Select an obstacle detection and avoidance quality appropriate for the traffic density and target hardware. Higher quality can improve sampling or response but costs more runtime work, so profile representative AI counts.
Some AI features might be disabled for some range of qualities.
Geometry Type
The type of geometry system used to treat static [https://docs.unity3d.com/Manual/class-GameObject.html](GameObjects) as obstacles.
Sensors/Front Sensors
To avoid obstacles, `AI Vehicle`s need sensors to detect them.
`Front Sensors` are the main sensors of any `AI Vehicle` and have two modes:
  • `Dynamic`: This mode allows the toolkit to change the sensors length & angle depending on their vehicle speed.
  • `Fixed`: By enabling this mode, the sensors length will be static and won't change.
Sensors Steer
This feature allows the [#settings-panel-artificial-intelligence--ai-sensors-front-sensors](Front Sensors) to steer in relation to their `AI Vehicle` steering angle.
Sensors Steer Multiplier
The sensors steering angle multiplier.
Sensors Length
The front sensors length.
The type of sensors length depends on the [#settings-panel-artificial-intelligence--ai-sensors-front-sensors](Sensors Mode). Here's a small recap for each mode:
  • `Dynamic`: An interval value with a minimum and a maximum.
    • `Min`: The minimum sensor length at 0 `Kilometres Per Hour (km/h)` / 0 `Miles Per Hour (mph)`.
    • `Max`: The maximum sensor length at 100 `Kilometres Per Hour (km/h)` / 62 `Miles Per Hour (mph)`.
  • `Fixed`: A single static number value.
Clamp Sensors Length
Setting this parameter to `No` allows the sensors length to exceed to its `Maximum` value.
This parameter is only available for `Dynamic` sensors.
Sensors Angle
The front side sensors angle.
The type of sensors angle depends on the [#settings-panel-artificial-intelligence--ai-sensors-front-sensors](Sensors Mode). Here's a small recap for each mode:
  • `Dynamic`: An interval value with a minimum and a maximum.
    • `Min`: The minimum sensor angle at 100 `Kilometres Per Hour (km/h)` / 62 `Miles Per Hour (mph)`.
    • `Max`: The maximum sensor angle at 0 `Kilometres Per Hour (km/h)` / 0 `Miles Per Hour (mph)`.
  • `Fixed`: A single static number value.
The sensors angle is always clamped between `0` and `90` degrees.
Clamp Sensors Angle
Setting this parameter to `No` allows the sensors angle to exceed to its `Maximum` value.
This parameter is only available for `Dynamic` sensors.
Setting the `Maximum` [#settings-panel-artificial-intelligence--ai-sensors-angle](Sensor Angle) to 90 degrees and enabling the [#settings-panel-artificial-intelligence--ai-clamp-sensors-angle](Sensors Angle Clamp) toggle won't make any change to the sensors behaviour. This only applies to `Dynamic` sensors.
Side Sensors Length
The length of side sensors for `AI Vehicle`s.

Behaviour & Physics
The Multiversal Vehicle Controller is all about physics, when it comes to that, we try to deliver the best advanced sets of configuration so developers can make the most of our systems and tweak values as they want. For this, the MVC provides a list of fields as mentioned below in this section.
Aerodynamic WingsPro
Aerodynamic wing modules and their runtime forces and movement require MVC Pro.

Downforce
When you enable `Downforce`, you get to use it within the `Stability` settings and when you configure your vehicle's `Active Aerodynamics`.
Air Anti-Roll
Air Anti-Roll applies corrective force while an airborne vehicle is rotating toward an unwanted orientation. It is primarily an arcade recovery aid; simulation-focused projects should test whether the artificial correction matches their handling goals.
Air Anti-Roll Intensity
The intensity/multiplier of forces applied to the vehicle.

Controls whether Stability and Aerodynamics can apply configured downforce while the vehicle has no ground contact.
Drag

Wheel Mass
Controls whether wheel mass is excluded from the mass used for the vehicle body's distribution and center-of-mass calculations. Revalidate total mass and handling after changing it.
Engine Mass
This feature is the same as the [#settings-panel-behaviour-and-physics-wheel-mass](Wheels Mass) feature, except that it has a much more noticeable effect in the vehicle's behaviour and relies on the `Engine Position` configuration of the `Chassis` component and on the [#settings-panel-engines-and-chargers-engine-preset-mass](mass of the vehicle's engine).
Steer Intensity
The mentioned field controls the player's steering input's intensity, the higher the value, the intense the vehicle steering, the lower this value is, the slower the vehicle steering responsiveness.
Steer Release Intensity
Just like [#settings-panel-behaviour-and-physics-steer-intensity](Steer Intensity), `Release Intensity` is meant to take control when the [#settings-panel-player-inputs-steering-wheel](Steering Wheel) input has been released or is inverting direction.
Steer Interpolation
The way in which the steering value should interpolate over time.
  • `Instant`: The steering value will instantly change to the target value.
  • `Linear`: The steering value will move constantly over time.
  • `Exponential`: This will let the steering value reach its target in a [https://en.wikipedia.org/wiki/Logarithmic_growth](Logarithmic Form) (i.e. fast at first and slow when reaching the target value).
Maximum Steer Angle
The maximum steering angle value for every vehicle.
Minimum Steer Angle
The minimum steering angle value for every vehicle.
Suspension AdjustmentsPro

Enabling this feature allows you to customize the vehicle's suspension stancing values, such as [https://en.wikipedia.org/wiki/Camber_angle](Camber), [https://en.wikipedia.org/wiki/Caster_angle](Caster) and [https://en.wikipedia.org/wiki/Toe_(automotive)](Toe).
Maximum Camber

Maximum Caster
The suspension's maximum [https://en.wikipedia.org/wiki/Caster_angle](caster angle) for every vehicle.
Maximum Toe
The suspension's maximum [https://en.wikipedia.org/wiki/Toe_(automotive)](toe angle) for every vehicle.
Maximum Side Offset

Launch Control
Launch Control is a feature commonly used in the automotive industry to get the best launch time out of a vehicle. Launch control usually acts like a normal RPM rev-limiter, but instead of limiting the RPM to the corresponding engine's [#settings-panel-engines-and-chargers-engine-preset-over-rev-rpm](Over-Rev RPM), this feature limits the vehicle's revving range to the engine's [#settings-panel-engines-and-chargers-engine-preset-peak-torque-rpm](torque peak RPM) when it's enabled. The mentioned feature is disabled by default at runtime, you can activate it using the [#settings-panel-player-inputs-turn-on-off-launch-control](Launch Control Input).
Counter Steering
Counter Steering is a stability feature that acts when a vehicle's rear wheels are slipping on one of their sideways axes. The counter steering system steers the vehicle automatically to the opposite of the vehicle's slipping direction to maintain stability.
Counter Steering Priority
This selection field is responsible for how the counter steering system should work, each option is described below:
  • `Steering Wheel`: The following option prioritizes the player's input over the counter steering system stability input.
  • `Average`: Using this option will let the steering system calculates the average between the counter steering system input and the player's input and applies the result value to the steering wheels.
  • `Counter Steer`: This option prioritizes the counter steering system's input over the player's steering input.
Counter Steer Intensity
The counter steer angle input multiplier.
Counter Steering Damping
This field smooths out the counter steering system angle input, the lower the value, the slower the counter steering to react and vice-versa.
NOS
Nitrous, commonly spelled as NOS thanks to the [https://en.wikipedia.org/wiki/Fast_%26_Furious](Fast & Furious) culture, is a method to boost engines in order to get more power and torque by adding a denser air composition called Nitrogen-dioxide (NO₂) inside the engine's air intake in order to get an efficient fuel burning process. NOS is usually stored inside bottles, which they differ in size, number and boost efficiency.
This feature is not available for EVs , since they use electric motors instead of internal combustion engines.
NOS Reloading
Enabling this feature will allow the player to get reproduceable amounts of NOS after consumption.
Delayed NOS
When both of the [#settings-panel-behaviour-and-physics-nos-reloading](NOS Reloading) and this feature are enabled, the reload system will have wait a for specific time span before regenerating NOS.
Regeneration Delay
The delay after the last use before NOS regeneration begins.
Progressive NOS
Progressive NOS has a huge effect on NOS bottles performance, the lower the NOS amount inside a specific NOS bottle, the lower the boost is and vice-versa.
One Shot NOS
When enabled, once the player activates the [#settings-panel-player-inputs-nos](NOS Input), he'll not be able to cancel boosting his vehicle's engine unless the currently used NOS bottle becomes fully empty.
Damage
Damage settings define the shared velocity thresholds, wheel-health behavior, explosion response, and material properties used by configured vehicles. Enable the global system before expecting local health or zone settings to respond.
Velocity Levels
The damage system used velocity levels to determine the intensity of the vehicle's collision or impact with other objects or vehicles. We can identify three levels: `Low`, `Medium` and `High`.
Wheel Health
Wheel Health tracks damage for each tire. Sustained skid, wheelspin, configured zones, or project code can reduce health until the tire becomes flat or fails, allowing the assigned [#settings-panel-visual-effects--vfx](visual effects) and changed wheel behavior to appear.
Wheel Damage Intensity
Controls the rate at which qualifying wheel stress damages the tire. Establish a repeatable skid or zone test before comparing intensity values.
Explosion Force
The force of the [#settings-panel-visual-effects--vfx-particle-systems-tire-explosion-force-field](Tire Explosion Field).
Rim Edge Emission Colour
The emission colour that will be visualized at the wheel's rim edges when at higher rates of heat caused by the friction between the metal of the rim and the ground the wheel is sitting on.
Rim Custom Emission Property
The emission property of the wheel's material, this property can be added when using a custom shaders to render the wheel object. The MVC systems can handle standard Unity shaders, HDRP and URP standard shaders as well. When using a custom built shader you'll have to assign this field in order to visualize the damage effect otherwise an error will be thrown in the [https://docs.unity3d.com/Manual/Console.html](Console window).

Camera Preset
A camera preset is an instance that contains the necessary information about the `Vehicle Follower`'s behaviour. You can switch between presets at runtime using the [#settings-panel-player-inputs-change-camera](Camera Switch Input). The preset settings can differ from a preset to another depending on their enabled features.
Name
The camera name is the preset identifier and cannot be a duplicate of another preset.
Type
The type field indicates the main behaviour type of the preset. A camera could be a `Follower` or a `Pivot`.
Features
Each camera preset exposes features compatible with its selected `Type`. The following list identifies the supported combinations:
  • `Vertical Orbit`: The camera can rotate around the vehicle's X axis. Available for `Follower` and `Pivot` type of presets.
  • `Horizontal Orbit`: The camera can rotate around the vehicle's Y axis. Available for `Follower` and `Pivot` type of presets.
  • `Speed Pulse`: This features allows the camera to go a bit backwards at higher speeds. Available for `Follower` type of presets.
  • Speed FOV : This feature allows the camera to feel like going backwards at higher speeds, by just changing its [https://docs.unity3d.com/ScriptReference/Camera-fieldOfView.html](Field Of View). Available for `Pivot` type of presets.
  • `Gear Pulse`: This features allows the camera to go a bit forward in a fast way while shifting gears, so the player can get the feeling of something happening. Available for `Follower` type of presets.
  • `Sideways Slip Pulse`: The camera can move left and right while the `target vehicle` is slipping on its X axis. Available for `Follower` and `Pivot` type of presets.
  • `Steering Tilt`: This feature will allow the camera to rotate around its Z axis, this rotation depends on the vehicle's velocity at the X axis. Available for `Follower` and `Pivot` type of presets.
  • NOS FOV : While the vehicle's NOS is active, the player will feel like the camera is moving backward in an intense way, by just changing its [https://docs.unity3d.com/ScriptReference/Camera-fieldOfView.html](Field Of View). Available for `Follower` and `Pivot` type of presets.
  • `Speed Shaking`: While running at higher speeds, the camera will simulate some shaking effects with a certain intensity. Available for `Follower` and `Pivot` type of presets.
  • `Off-Road Shaking`: Off-Road grounds can be configured in the [#settings-panel-grounds-and-surfaces](Grounds & Surfaces) panel, and if the `target vehicle` is on top of one of these grounds and this feature is enabled, the player will get that feeling of the vehicle running on top of something rough. Available for `Follower` and `Pivot` type of presets.
  • `NOS Shaking`: The camera will shake randomly in case the vehicle's NOS is active. Available for `Follower` and `Pivot` type of presets.
  • `Sideways Slip Shaking`: As the vehicle's absolute [https://docs.unity3d.com/ScriptReference/WheelHit.html](sideways slip) value gets higher, the camera starts to shake randomly. Available for `Follower` type of presets.
  • `Forward Slip Shaking`: The camera will shake in case the vehicle's [https://docs.unity3d.com/ScriptReference/WheelHit.html](forward slip) value is positive. The higher the slip value, the intense the shaking is. Available for `Follower` type of presets.
  • `Brake Slip Shaking`: The camera will shake in case vehicle's [https://docs.unity3d.com/ScriptReference/WheelHit.html](forward slip) value is negative. The lower the slip value, the intense the shaking is. Available for `Follower` type of presets.
  • `Showcase`: When the `target vehicle` is idle for a period of time, the camera will rotate around the vehicle in slow-motion to visualise it in a cinematic way. Available for `Follower` type of presets.
  • `Stunts Showcase`: While doing stunts with the `target vehicle` like [https://google.com/search?q=car+donuts](donuts), the camera will stay in an idle position for a better cinematic view. Available for `Follower` type of presets.
  • `Obstacles Detection`: This feature will make the camera dodge intensely in case its `target vehicle` collides with an object or another vehicle. Available for `Follower` and `Pivot` type of presets.

Engine Preset
An engine can be found in any type of vehicle as its responsible for movement by delivering torque and power to the `Vehicle Wheel`s.
In this section we're going to explain every single option and configuration so you can create your own engine preset with ease.
Every parameter has its own effect on the behaviour, inertia or performance of the engine or the vehicle even in small/un-noticeable ways.
You can use the button to modify the current engine in a separate configuration window that has the same parameters and settings mentioned below.
Name
Is the engine identifier, each engine has its own unique name and cannot match with any other engine preset.
Alignment
Each engine has its own alignment configuration, and everything related to the engine relies on this parameter. The available options are mentioned below:
  • `Inline`: An `Inline` internal combustion engine have its cylinders arranged in straight form.
  • `V`: `V` engines are like two `Inline` blocks, except they're combined together in a V shape.
  • `Boxer`: Commonly known as `Flat` engines, are the same as `V` engines except that this kind of configuration combines two `Inline` blocks in a perfect flat angle.
  • `W`: This kind of engines is basically formed of two `V` engines combined together.
  • `Rotary`: Commonly referred to as a [https://en.wikipedia.org/wiki/Wankel_engine](Wankel) engine, is un-like normal internal combustion engines that use cylinders, Rotary engines are made out of a block containing a triangular shape rotating around a central axis, called the `Central drive shaft`.
  • `Electric`: As the name suggests, `Electric` engines are basically electric motors that work with electricity instead of normal fuel (i.e. `Gas` or `Diesel`)
Fuel Type
This indicates the fuel type of an internal combustion engine, it's going to be either `Gas` or `Diesel`. Note that this parameter is not available for `Electric` engines. As for `Rotary` engines, this parameter will be locked to `Gas` only.

The RPM at which the engine is Over-Revving.

Engine Folder Setup
Every Engine Preset can have a folder where it can store audio clips of the engine sound and later used by the MVC audio systems. These folder can be located under the main [#setup-wizard-audio-folder-path](Audio Folder), within the `Engines Folder`.
The default path of the mentioned directory is the following: `Assets/Resources/<Audio Folder>/<Engines Folder>/<Engine Name>`.
Example: `Assets/Resources/Audio/Engines/V8NM 4.0L P60B40`
The structure of the engine folder is the following:
  • `<Engine Name>`: The main engine directory

    • `Engine`: This folder contains the vehicle's engine sound. (Optional in case the `Exhaust` folder is available)

      • `<Engine Audio Clips Here>`: Acceleration/Deceleration audio clips. (Optional in case of using `Accel` & `Decel` folders)

      • `Accel`: For acceleration audio clips. (Optional in case of using audio clips inside the `Engine` folder directly)
        • `<Engine Acceleration Audio Clips Here>`
      • `Decel`: For acceleration audio clips. (Optional - See `Accel` folder notice above)
        • `<Engine Deceleration Audio Clips Here>`

    • `Exhaust`: This folder contains the vehicle's exhaust sound. (Optional in case the `Engine` folder is available)

      • `<Exhaust Audio Clips Here>`: Acceleration or Deceleration audio clips. (Optional in case of using `Accel` & `Decel` folders)

      • `Accel`: For acceleration audio clips. (Optional in case of using audio clips inside the `Exhaust` folder directly)
        • `<Exhaust Acceleration Audio Clips Here>`
      • `Decel`: For acceleration audio clips. (Optional - See `Accel` folder notice above)
        • `<Exhaust Deceleration Audio Clips Here>`
It's unnecessary to have an `Exhaust` folder for an `Electric` engine as exhaust sounds are not available for EVs in real-life.
Audio clips inside the specified folders should meet the following naming requirements in order to get recognized by the MVC audio systems:
Every audio clip represents a RPM level of the sound.
To separate between numbers and unrelated text within the audio clip name, the audio systems uses a `Name Separator`, which is defined in the `Sound Effects` panel. The default value of this separator is `_`.
The separator can be located anywhere in the audio clip name, just make sure it separates the RPM value.
You can also use only RPM values to name your audio clips.
Here's a quick recap of the requirements mentioned above:
  • `engine-name_<RPM>.wav`
  • `engine_name_<RPM>.wav`
  • `<RPM>_engine_name.mp3`
  • `<RPM>_engine-name.wav`
  • `some_text_<RPM>_engine_name.mp3`
  • `<RPM>.wav`
Here are some wrong examples that are incorrect:
  • `engine-name<RPM>.wav`
  • `<RPM>engine_name.wav`
  • `<RPM>-engine_name.wav`
  • `some_text-<RPM>_engine_name.mp3`
  • `abcd<RPM>.wav`

Supercharger Preset
[https://en.wikipedia.org/wiki/Supercharger](Superchargers) are a famous type of engine aspiration components that blows compressed dense air into an internal combustion engine to get more power.
Supercharger Type
Superchargers have a variety of types:
  • `Roots`: One of the `Positive Displacement` chargers. This type of superchargers is commonly used in old American Muscle cars with [https://google.com/search?q=supercharger+hood+blower](Hood-blowers). In real-life, this type gives lower-boost values compared to `Twin Screw` superchargers due to its old-tech components.
  • `Twin Screw`: One of the `Positive Displacement` chargers. This type of superchargers is usually used by the majority of vehicles. In real-life, this type gives higher-boost values compared to `Roots` superchargers due to the usage of high-tech components.
  • `Centrifugal`: A `Centrifugal` supercharger is very similar to a turbo in terms of performance, except it uses a belt linked to the engine crank instead of using exhaust gases to drive the charger. This type of superchargers provide high levels of boost at high RPMs (higher than `Positive Displacement` superchargers in real-life) and lower boost levels at low RPMs, just like [#settings-panel-engines-and-chargers-charger-preset-turbocharger-preset](Turbocharger)s.

The supercharger boost multiplier at high RPMs.

Tire Compounds
The Tire Compounds tab stores reusable tire definitions independently from a vehicle. Select or create a compound, give it a stable name that describes its physical intent—such as road, sport, drift, wet, or off-road—and configure the friction representation required by the active wheel-physics integration. The Vehicle inspector then assigns a compound to the relevant wheels or axle group.
Friction complexity
Complexity controls how much of the available tire model is evaluated. Choose the simplest representation that preserves the intended handling and use a repeatable driving test before increasing complexity. More detailed curves cannot repair a wheel that has incorrect geometry, no ground contact, or an unsuitable suspension.
WheelCollider curve
The WheelCollider-style curve uses extremum and asymptote slip/value pairs to shape initial grip, peak force, and the falloff after the peak. Keep slip points ordered and avoid abrupt shapes unless the desired tire should lose grip sharply. Test acceleration, threshold braking, and steady cornering because one curve affects several driving situations.
Pacejka curve
Pacejka-capable integrations use Magic Formula coefficients to describe the force relationship over tire slip. These controls appear only after MVC discovers an integration that declares Pacejka friction support. `Fit From Slip Curve` derives a practical starting point from the Unity-style curve, while `Manual` exposes B, C, D, and E for direct authoring. Use `Refresh Fits` after changing the source curves. An automatic fit is a migration aid, not certification of real tire data.
The optional [#custom-wheel-colliders](Pacejka Wheel Collider workflow) explains how to install the official integration, migrate existing compounds, test alignment, and return safely to Unity Wheel Collider. Tune every representation with the target vehicle load, tire width, ground surface, and a repeatable route.
Width modifier and portability
Width modifiers let the compound account for supported changes in tire width without creating a new preset for every wheel. Tire preset import/export can move reusable tuning between projects. Preserve preset names when vehicle configuration files reference them, and verify integration compatibility after import.

Editor tools
MVC is designed around guided Unity Editor workflows. The custom menus and inspectors create the required hierarchy, expose only the settings that apply to the current configuration, and report problems before they become difficult runtime bugs. This chapter explains those visual interfaces and the responsibilities that remain with the developer.
Most creation commands are available from both `GameObject > MVC` and `Tools > Multiversal Vehicle Controller > New`. Prefer these commands over adding hidden MVC components manually. A creation command can supply required child objects, colliders, references, layers, or defaults that a raw `Add Component` operation cannot infer safely.
Creating MVC objects
Use `Tools > Multiversal Vehicle Controller > New` when the selection in the Hierarchy is not important. Use the matching `GameObject > MVC` command when you want Unity to place the new object relative to the currently selected GameObject. The validation functions attached to these commands prevent creation while the toolkit is not installed or while an incompatible selection is active.
Core scene objects
A typical playable scene contains one `Vehicle Manager`, one `UI Controller` associated with that manager, one `Vehicle Follower` for player cameras, at least one `Ground Mapper`, and one or more vehicles. The manager coordinates registration and chooses the active player vehicle. The other objects read that selection instead of keeping unrelated copies of the player state.
Vehicle objects
`New > Vehicle` creates the root and opens the vehicle-oriented inspector. From there, configure the chassis, wheels, exhausts, drivetrain, handling, audio, and optional systems. `New > Trailer` creates the trailer variant of the same vehicle foundation. Supporting objects
Dedicated commands create AI paths, followers, UI controllers, ground mappers, drivers, camera pivots, wheel-spin effects, and zone objects. A generated object is still only a starting point. Inspect the status icon in every MVC inspector, expand any problem message, and assign the project-specific references that the creation command cannot know.
Do not duplicate singleton-style scene objects casually. Two managers, two active UI controllers, or multiple followers competing for the same camera can make the scene appear to work until registration order changes.
Install, repair, and backups
The `Install/Repair` command reopens the installation workflow when package files or project settings need to be checked. Run it after a failed import, a package upgrade that stopped during compilation, or a project-settings merge that removed required tags, layers, scripting symbols, or package dependencies. Let Unity finish compiling before interpreting the next message from the wizard.
`Settings > Backup > Create` stores the MVC settings state before an experimental change or upgrade. `Settings > Backup > Restore` restores a compatible backup. A settings backup is not a substitute for source control: it does not protect scene hierarchies, vehicle prefabs, custom materials, input assets, or third-party packages.
`Repair > Fix Missing Components` is intended for broken MVC hierarchies whose serialized component references no longer resolve. `Repair > Enforce Asset GUIDs` addresses asset identity problems. Use these targeted tools only after creating a project checkpoint, and review the Console after the operation. Repeated repair without identifying why assets keep disappearing can hide a package or version-control problem.
  • Back up the project or commit the working tree.
  • Exit Play Mode and allow compilation to finish.
  • Run the narrowest repair command that matches the symptom.
  • Resolve the first Console error before later cascading errors.
  • Open the Settings Panel and a representative vehicle to confirm that references and presets still resolve.
Vehicle configuration import and export
The `Vehicle Configurations` header in the Vehicle inspector contains `Import` and `Export` actions. They transfer tuning rather than scene construction, so select only the configuration groups that should move between vehicles. Numbers, enumerators, curves, and supported section data travel in the configuration file; transforms, renderers, mesh bounds, scene objects, and other scene references deliberately remain with the destination vehicle.
Engine, charger, and tire selections are stored by stable names so MVC can resolve matching presets in another project. A name is therefore part of the portable configuration contract. Renaming a preset after export can make the destination unable to restore that selection even though the numerical sections still import correctly.
Export workflow
  1. Select the source vehicle outside Play Mode.
  2. Click `Export` and select the tuning sections that should travel.
  3. Use `Select All` only when the destination should inherit the complete supported tune.
  4. Save the JSON file with the vehicle, purpose, and date in its filename.
  5. Keep the file under source control with any project-specific setup notes.
Import workflow
  1. Duplicate or otherwise back up the destination prefab.
  2. Click `Import`, choose the configuration file, and read the source vehicle, export date, and MVC version shown by the inspector.
  3. Select only compatible sections. Unsupported sections are identified separately and are not silently invented.
  4. Apply the import, then inspect preset references and all diagnostic icons.
  5. Run a controlled baseline test before accepting the new tune.
An import can produce valid data that is unsuitable for the destination vehicle. A long-wheelbase truck and a lightweight sports car may accept the same steering or suspension fields but behave very differently.
Vehicle Profiler
Open `Tools > Multiversal Vehicle Controller > Vehicle Profiler` or use the chart button in a Vehicle inspector. The profiler presents live vehicle state in logical groups so a developer can separate configuration problems from visual symptoms. Read it alongside the vehicle, wheel, and AI inspectors while repeating the same controlled test after changing one group of values.
In both Community and Pro, use the profiler to confirm that player inputs reach the selected vehicle, engine RPM and transmission state change as expected, wheel contacts are valid, and assistance systems engage for a reason. A static value is not automatically an error; first confirm that the related feature is enabled and that the current test should exercise it.
AI and guarded profiler dataPro
The profiler's AI view and values belonging to Pro-only vehicle systems appear only in MVC Pro. The profiler window and its core vehicle, drivetrain, input, light, wheel, and Rigidbody views are available in both editions.
A disciplined profiling pass
  1. Choose one vehicle and one short, repeatable route.
  2. Record the initial symptom and the profiler values that correspond to it.
  3. Change one settings group, such as tire friction or gear ratios.
  4. Repeat from the same position with the same inputs.
  5. Compare behavior and data, then keep or revert the change.
The profiler explains what the controller is doing; Unity's Profiler explains how much CPU, memory, rendering, and physics work the project is doing. Use both when the complaint is performance rather than tuning.
Components and behaviours
MVC components form a connected simulation rather than independent scripts. The reference below focuses on what users can create, assign, and tune in Unity. API members and code-only extension contracts remain in the API reference.
Read the dependency descriptions before treating an inspector field as an isolated value. For example, engine output is filtered by transmission ratios and differential behavior before it reaches driven wheels; wheel friction then depends on the selected tire compound, ground mapping, wetness, load, and the active physics integration. Vehicle Manager
Create: `GameObject > MVC > Manager`
Role: vehicle registration, player selection, ground coordination, and global runtime state
Scene requirement: one active manager for the coordinated vehicle systems
The manager discovers and coordinates active vehicles, distinguishes player-controlled and AI-controlled entries, exposes the current player to the UI and camera systems, and keeps ground mapping available to wheel calculations. Components that need the current player should use this coordinated state rather than independently searching the scene every frame.
Player assignment
Confirm that the intended vehicle is registered and selected before diagnosing input, camera, or UI failures. A perfectly configured speed meter still displays no useful data when the manager has no active player. When changing players at runtime, perform the switch through the supported manager workflow so camera, UI, input, and vehicle state remain synchronized.
Grounds and scene lifetime
The manager cooperates with Ground Mapper components and active vehicles over the life of the scene. If scenes are loaded additively, decide which scene owns the persistent manager and prevent duplicates. When a vehicle is spawned or destroyed dynamically, verify that registration is added and removed cleanly rather than retaining stale references.
If several systems fail together—no UI values, no follower target, and no input response—check the manager and active player before debugging each dependent component separately.
Vehicle
Create: `GameObject > MVC > Vehicle`
Required foundation: Rigidbody, chassis, configured wheels, and at least one driven wheel
`Vehicle` is the root behavior that brings together component references, inputs, simulation modules, presentation state, diagnostics, and optional gameplay systems. Its inspector intentionally follows dependency order. Complete `Components` first; performance and handling cannot be evaluated while the chassis, wheels, or driven-wheel assignment is invalid.
Components
Assign the chassis, wheels, and exhausts that belong to this root. The wheel list establishes axle location, side, steering role, braking role, driven state, render transforms, tire data, and physics backend. Do not share a wheel component between vehicle roots. A diagnostic warning in this foldout usually invalidates later measurements.
Performance and transmission
Performance selects or overrides the engine and optional charger, defines mass-related behavior, and enables systems such as fuel or battery consumption and Nitrous where available. Transmission determines how the usable engine range becomes wheel torque through gearbox mode, clutch behavior, ratios, final drive, and differentials. Tune engine output, gearing, and differential behavior as one drivetrain. The displayed theoretical top speed is a calculation, not a promise that the engine can overcome drag and rolling resistance.
Brakes, steering, suspensions, tires, and stability
These foldouts form the handling stack. Brakes provide per-axle stopping torque and heat behavior. Steering defines geometry, range, and response. Suspension controls spring travel, stiffness, damping, camber, caster, toe, and offsets. Tires select the friction model and compound. Stability adds intervention such as anti-lock braking, traction control, stability control, counter-steer, downforce, anti-roll, and related assistance. Change one layer at a time and retest on the same road.
Audio and optional systems
Audio connects engine, charger, transmission, ground, impact, exhaust, and mixer data. Trailer Link is available when the vehicle should tow a trailer. Fields that depend on a global setting remain hidden or disabled until that setting is enabled.
The status icons summarize warnings, errors, and issues per foldout. Expand and resolve them in dependency order instead of suppressing the visible symptom with extreme tuning values.
Pro vehicle modulesPro
The Vehicle inspector's AI, Interior, Driver IK, fuel/battery, advanced-zone, and other explicitly guarded modules require MVC Pro.
Vehicle Chassis
The chassis owns the physical body and the render groups that are not wheels. It connects the Rigidbody, body colliders, engine position, light definitions, aerodynamic wings, damageable chassis parts, and follower pivots. Configure its colliders and reference groups before adding optional moving or damageable parts. Keep the chassis transform stable and use children for movable mechanisms or visual offsets.
Collider geometry should approximate the body without becoming unnecessarily detailed. Avoid overlapping wheel colliders, placing the main collider below the road, or building a compound collider from dozens of tiny shapes. The engine-position reference influences weight-related calculations and visual diagnostics. Position it meaningfully even when the engine mesh is not visible.
Light groups link MVC light behavior to material emission and Unity `Light` sources. Chassis parts describe detachable or damageable exterior pieces and their joint relationships. Follower pivots provide vehicle-specific interior and close-up camera positions.
Aerodynamic wings and advanced chassis controlsPro
Aerodynamic wing modules, engine-torque chassis response, Anti-Ground Colliders, and collider-ignore controls require MVC Pro.
Wing modules model fixed or moving aerodynamic surfaces and can contribute downforce and drag. Advanced collider controls prevent selected body colliders from interacting with configured ground surfaces; use them only after the ordinary chassis collision shape is valid.
Vehicle Wheel
A Vehicle Wheel bridges the physics integration and the visible wheel assembly. Every wheel needs the correct side, axle role, physics configuration, and visual reference. Its identity describes side and drivetrain role; its wheel module tracks rotation and dimensions; suspension and friction modules define contact response; SFX and VFX modules express that contact through sound, particles, marks, heat, and damage.
Geometry and assignment
Place the physics center at the actual wheel center and match radius to the tire, not the rim. Assign the visual wheel transform so steering and spin apply to the correct object. Split rim and tire meshes when tire-health and wheel-spin presentation need to treat them differently. Verify left/right orientation and driven/steered/braked roles before tuning forces.
Contact and friction
Wheel contact produces load, slip, angular velocity, compression, and resolved ground data. The selected tire compound converts those values into longitudinal and lateral response. A wheel that reports no ground contact cannot be fixed by increasing engine power. Check radius, suspension reach, ground collision, project layers, and the selected integration first.
Custom physics selectionPro
Selecting and configuring an external wheel-physics integration requires MVC Pro; Unity Wheel Collider remains available in Community.
MVC discovers compatible wheel-physics integrations and exposes them through General settings. Importing a wheel asset alone is not enough: it must provide an adapter that implements MVC's integration contract. Follow [#custom-wheel-colliders](Custom wheel colliders) for the Pacejka import, migration, validation, and rollback workflow. Integration capabilities can change how anti-sway, friction, alignment, and contact data behave, so do not assume that settings tuned for Unity WheelCollider produce the same result on another backend.
Drivetrain presets and components
Engine, charger, differential, and exhaust data are reusable building blocks. The Settings Panel stores project-level presets, while the Vehicle inspector chooses which presets and overrides apply to one vehicle. Stable names matter because configuration import resolves several preset references by name.
Vehicle Engine
An engine preset defines fuel type, engine type and position, mass, minimum RPM, redline, over-rev range, maximum RPM, torque and power curves, and audio behavior. Keep RPM thresholds in a logical order. The curve should describe usable output rather than compensating for incorrect gear ratios or vehicle mass.
Vehicle Charger
A turbocharger or supercharger modifies a compatible combustion engine. Configure boost behavior, mass and placement effects, compatible engine names, and transient audio. Confirm that the selected charger type matches the Vehicle aspiration setting. Electric drivetrains and incompatible engines should not be forced through charger configuration.
Vehicle Differential
Differentials distribute input torque between outputs. Open, locked, limited-slip, and supported custom behavior produce different results when wheel speeds diverge. Assign only the wheels belonging to that differential and use a coherent final ratio. Extreme locking can create understeer or tire scrub; an overly open setup can send useful torque to the wheel with least traction.
Vehicle Exhaust
Exhaust components define output positions and connect exhaust smoke, flame, blowout, and audio events to the vehicle. Orient the output away from the body and check the gizmo in Scene view. Particle orientation or scale errors should be corrected at the effect or pivot rather than by rotating the entire vehicle.
Tire compounds and Ground Mapper
A tire compound describes how a tire responds to slip and load. A ground preset describes the surface under it, including friction modifiers, roughness, sound, particle effects, mark material, and environmental values. Community projects can tune the required default tire compound and default ground preset.
Multiple presets and surface mappingPro
Multiple named tire or ground presets, their import/export tools, and Ground Mapper surface assignments require MVC Pro.

Use the Ground Mapper inspector and wheel runtime data to identify the resolved surface before changing friction.
Pacejka and WheelCollider curvesPro

MVC can store friction data for Unity-style WheelCollider behavior and Pacejka-based integrations. Vehicle Follower and camera pivots
Vehicle Follower applies the active camera preset to the Vehicle Manager's player vehicle and manages camera creation, switching, placement, field of view, orbit input, obstacle handling, showcase behavior, and multiple shake sources. Camera presets live in Settings so several vehicles can share the same baseline. Follower pivots live on a vehicle because interior, bumper, wheel, and cinematic positions depend on that model.
Test a preset at zero speed, normal driving speed, the configured maximum speed, reverse, and near obstacles. Then trigger each enabled shake source separately. If every effect is combined during the first test, it becomes difficult to identify whether uncomfortable motion comes from speed, slip, impact, off-road, NOS, or a badly positioned pivot.
Camera collision and obstacle response cannot repair a pivot that begins inside the chassis collider. Validate the pivot and near clip plane before increasing avoidance strength.
Vehicle UI Controller
The UI Controller reads the Vehicle Manager's active player and distributes live values to Speed Meter and Mobile Input Preset modules. Needles can represent radial rotation or fill-style movement. Text modules display values such as speed, RPM, and gear. Sprite modules communicate states such as ABS, ESP, TCS, handbrake, and indicators through configured normal, active, and disabled colors. Validate each element by triggering the real vehicle state, not by assuming an assigned reference is sufficient.
Mobile presets map buttons, joysticks, and supported sensor axes to the same vehicle actions used by desktop input. Presets make several control layouts switchable without rebuilding the vehicle. Check release state as carefully as pressed state; a pedal that remains nonzero after touch release makes the vehicle appear to have a physics fault.
AI paths and path followersPro
Vehicle AI Path generates a reusable route from editable curve controls, creates spaced path points, optionally aligns those points to the ground, and provides visualization data. Keep curves smooth enough for the intended vehicle and choose point spacing that captures corners without producing unnecessary work on long straight sections.

System behaviour guides
These guides connect settings and components that participate in the same runtime behavior. Use them when every individual reference appears valid but the complete system does not produce the expected result.
MVC evaluates a configured vehicle in layers: project settings define available systems and reusable presets; scene components provide managers and environmental context; the Vehicle collects input and state; wheel physics resolves contact; drivetrain and handling modules calculate forces; presentation modules convert state into sound, visuals, camera motion, and interface feedback.
Initialization and scene lifetime
A reliable scene begins with valid project settings and one authoritative manager. When a Vehicle becomes active, its serialized component graph must already contain a chassis, Rigidbody, wheels, and the presets needed by enabled modules. The manager then registers the vehicle and exposes the correct player selection to dependent systems.
Before Play Mode
  • The Setup Wizard has completed and the Settings asset resolves.
  • Required Unity packages compile without errors.
  • Vehicle and wheel layers are distinct and follow the Settings Panel.
  • The vehicle diagnostic icons contain no blocking component errors.
  • The scene has one intended Vehicle Manager and any required follower, UI controller, or ground mapper.
Dynamic vehicles
Spawn the complete configured prefab rather than assembling a partial vehicle over several frames. If runtime code must add components, keep the object inactive until required references exist, then enable it so registration observes a coherent state. When destroying or pooling the vehicle, disable it through the expected lifecycle so manager lists, native data, audio sources, UI targets, and AI behavior do not retain stale state.
Additive scenes
Choose whether the manager, follower, and UI are persistent or scene-owned. A persistent manager should not be duplicated by every loaded gameplay scene. A scene-owned manager should not leave a persistent vehicle pointing at a destroyed service. Establish this ownership in the project architecture instead of relying on whichever object awakens first.
Physics and wheel-contact flow
During fixed simulation updates, MVC gathers vehicle inputs and module state, updates drivetrain targets, asks the active wheel integration for contact and friction behavior, and applies the resulting forces and torques to the Rigidbody. Unity Wheel Collider can divide that interval into the configured substeps; another backend can expose different integration-owned solver settings.
The physics selection is not merely a different collider component. An integration reports supported capabilities and can differ in friction representation, anti-sway application, alignment, contact data, interpolation requirements, and settings. MVC creates each wheel's backend through the selected integration and falls back to Unity Wheel Collider when the saved integration is missing or unavailable. Re-test suspension, tires, stability assists, and wheel visuals after changing integrations. Never compare backends while also changing tire curves and vehicle mass.
External physics integrationsPro
Selecting an external backend, including Pacejka Wheel Collider, requires MVC Pro. Unity Wheel Collider supplies the shared baseline.
Optional backend: [#custom-wheel-colliders](Import and migrate to Pacejka Wheel Collider), or review the same chapter for the contracts required by another custom integration.
When a wheel reports no contact
  1. Inspect wheel center, radius, suspension direction, and suspension reach.
  2. Confirm the ground collider or Terrain participates in physics and is on an allowed layer.
  3. Confirm the wheel is assigned to the correct vehicle and active integration.
  4. Verify the default ground selection; in MVC Pro, inspect Ground Mapper only after physical contact exists.
  5. Use runtime wheel statistics before increasing spring, grip, or engine values.
When contact is unstable
Look for excessive Rigidbody mass ratios, a center of mass outside the body, collider overlap, unrealistic spring stiffness, insufficient damping, a fixed timestep inappropriate for the target speed, or too few substeps. Raising every stability assist can mask the problem in one maneuver while making another maneuver worse.
Drivetrain and energy flow
The engine defines the usable RPM range and torque source. An eligible turbocharger or supercharger modifies that source. The clutch controls connection to the transmission. Gear ratios and final drive convert angular speed and torque. Differentials distribute the result, and only wheels assigned to the drivetrain receive motor torque.
Engine validation
Minimum RPM, redline, over-rev, and maximum RPM should form a sensible progression. The torque and power curves should describe the same engine intent. If acceleration is weak, confirm throttle input and clutch engagement before increasing power. If RPM immediately reaches the limiter, inspect driven-wheel contact, ratios, and clutch transfer.
Gearing and top speed
Short ratios multiply torque strongly but finish their useful speed range earlier. Tall ratios can support more theoretical speed but may leave the engine below its effective power range. Tune one transmission on a consistent route and review launch, shift RPM, acceleration between shifts, and speed at the same marker. Theoretical top speed does not include every real drag and traction limitation.
Fuel and batteryPro
Fuel and battery consumption, depletion, refill, and recharge simulation require MVC Pro.
Fuel or battery consumption gates continued power delivery. Time-based consumption spends energy while the engine or motor operates according to the selected behavior. Distance-based consumption ties usage to travel. Capacity, current level, refill or recharge behavior, and depletion response must agree with the vehicle type. An electric vehicle should use the battery-oriented workflow and should not be forced through combustion-only systems such as engine stall or forced induction.
Controlled comparison
Measure a baseline before assigning a new engine, charger, tire, or ratio set. Repeat from the same starting point and avoid changing handling at the same time. More power frequently exposes wheelspin, unsuitable differential behavior, excessive intervention, or gearing that was acceptable only with the weaker baseline.
Handling, braking, and stability
Handling is the combined result of wheel geometry, steering, suspension, tires, mass distribution, aerodynamics, and electronic assistance. Treat the systems in that order. An assistance system should refine a plausible physical setup, not constantly fight impossible geometry.
Steering
Simple steering follows the configured input relationship directly. Dynamic methods can reduce or reshape response with speed. Ackermann behavior changes inner and outer wheel angles to follow different turning radii. Confirm wheelbase, track width, steer-wheel assignment, and pivot orientation before interpreting the method.
Suspension
Spring length determines available travel; target, stiffness, and damping determine where the vehicle settles and how it responds. Begin with symmetrical values on a flat surface and record resting compression before aggressive tuning.
Alignment adjustmentsPro
MVC's camber, caster, toe, stance, and side-offset controls require MVC Pro. External physics integrations also require Pro.
With Unity Wheel Collider, MVC's alignment adjustments are visual. A capable custom backend can apply supported values physically; the Pacejka integration applies camber, caster, and toe through its collider.
Brakes and heat
Brake torque applies per configured brake. Balance front and rear values according to mass distribution and tire capacity. Brake heat can remain visual or reduce performance when enabled. Validate cold stopping first, then repeated stops, heating, cooling, and recovery. A vehicle that pulls sideways usually has assignment, contact, or left/right configuration differences rather than a need for more total torque.
Stability systems
ABS limits wheel lock while braking. TCS limits driven-wheel slip under power. ESP or stability behavior counters unwanted rotation or divergence. Counter-steer, anti-roll, downforce, and air behavior address other parts of the handling envelope. Test each feature with a maneuver that actually activates it and watch its UI indicator, runtime Inspector state, or Vehicle Profiler data.
Tire and ground interaction
Default tire and ground response
The wheel first needs physical contact. The selected tire compound and default ground preset determine physical response, rolling and skid audio, particles, and wheel-mark materials in Community and Pro.
Map multiple surfacesPro
Ground Mapper and switching among multiple named tire or ground presets require MVC Pro.
Ground Mapper resolves Terrain layers or Collider properties to a named ground preset. That resolved ground can select distinct friction modifiers, damaged-tire audio, particles, and wheel-mark materials for each surface.
When a road sounds or looks like the wrong surface, inspect the resolved ground index rather than editing audio at random. When the correct surface is resolved but handling is wrong, separate tire friction from ground modifiers and wetness. When only one wheel disagrees, compare that wheel's contact point and the exact Terrain layer blend or collider beneath it.
Surface authoring orderPro
This multiple-surface authoring and mapping sequence requires MVC Pro. Community users should tune and test the existing default preset without the create, name, or map steps.
  1. Create and name the ground preset.
  2. Configure its physical friction and roughness intent.
  3. Add optional audio, particles, and mark materials.
  4. Map Terrain layers or Colliders to the preset.
  5. Test one wheel at low speed, then a complete vehicle across boundaries.
  6. Test wetness and damaged-tire variants only after the dry baseline works.
Audio routing and behavior
MVC audio is distributed across global SFX settings, engine and charger presets, ground presets, vehicle sources, exhausts, and reverb zones. The global Audio Folder Path must remain under a Unity `Resources` folder because runtime loading depends on that path. Engine folder and filename conventions allow clips to be associated with RPM levels.
Engine clips represent recorded RPM points. MVC pitches and blends neighboring clips as engine speed changes. The configured name splitter identifies the numerical part of a filename. A folder mismatch or unparseable filename can leave a valid engine preset without a usable runtime clip set.
Mixers and source groups
Use mixer groups to separate engine, ground, transmission, impact, exhaust, NOS, and other categories. Balance source clips and group levels before pushing Global Volume. A clear routing structure makes pause, interior filtering, reverb, and accessibility settings easier to implement later.
Transient effects
Impacts, gear changes, exhaust blowouts, charger blowouts, NOS loading, and other events should be tested at realistic frequency. A dramatic clip that sounds good once may become exhausting when triggered on every small contact. Validate trigger thresholds and randomization as well as volume.
Reverb zonesPro
Vehicle Zones Container and Audio Reverb Zone authoring require MVC Pro.
A reverb zone represents a physical acoustic area such as a tunnel or garage. Match its shape to the environment, test entry and exit at different speeds, and listen for abrupt transitions. When several zones overlap, confirm which reverb behavior should dominate rather than accepting unpredictable stacking.
Visual-effects behavior
VFX settings provide global defaults and assets, while vehicle, wheel, chassis, exhaust, and ground data decide when an effect appears. Ground particles depend on resolved contact and slip. Wheel marks depend on contact sampling and surface material. Exhaust effects depend on engine and event state. Brake heat depends on repeated braking and configured temperature response.
MVC culls supported effects relative to the active camera and effect bounds. Culling is a presentation optimization; it should not change vehicle physics. If an effect disappears too early, inspect its bounds, source transforms, active camera, and global VFX settings before disabling culling for the whole project.
Authoring rules
  • Keep particle systems oriented and scaled correctly at their source pivots.
  • Use ground-specific assets only after ground mapping is verified.
  • Test emission at low and high frame rates.
  • Limit mark lifetime and sampling to the visual requirement.
  • Check transparent materials in every supported render pipeline.
  • Validate effects from the actual player camera, not only the Scene view.
Input, camera, UI, and mobile flow
Player controls begin in the selected input backend. MVC maps named inputs to vehicle actions. Vehicle Manager identifies the player, Vehicle applies the controls, Vehicle Follower reads camera actions and vehicle state, and UI Controller displays the same selected vehicle while mobile presets can write into equivalent actions.
Input backend
Inputs Manager is built on Unity's modern Input System and supports keyboard and device bindings through a beginner-oriented editor. Legacy Input Manager remains for projects that depend on named legacy axes. Confirm the active backend before debugging an individual binding. An input created in one system does not automatically exist in the other.
Analog and button actions
Steering, fuel, brake, and clutch usually benefit from analog ranges. Gear shifts, engine start, horn, reset, lights, signals, hazards, camera switching, NOS activation, and trailer linking usually behave as button actions. Apply dead zones and polarity at the appropriate input source instead of compensating with unrelated vehicle tuning.
Gamepad rumble
Rumble can respond to configured speed levels and supported vehicle events. Camera shake and controller vibration may share an intensity source or be tuned independently. Test them separately first; strong camera motion can make weak handling feel worse, while excessive vibration can hide the exact event that triggered it.
Mobile controls
Mobile Presets connect UI buttons, joysticks, or supported sensors to actions. Validate axis, polarity, press, hold, release, multitouch, safe areas, and orientation. Unity's Simulator is useful for assignment checks, but a physical device is required for comfort, sensor behavior, latency, and real multitouch validation.
AI execution and tuning orderPro
AI path following turns route position, direction, target speed, corner anticipation, traffic policy, obstacle samples, and recovery state into steering and pedal targets. Those targets still pass through the normal vehicle drivetrain and handling. An AI controller cannot make an underpowered or gripless vehicle follow an impossible route.
  1. Validate the vehicle under direct control.
  2. Create a smooth path and verify its spaced points and ground alignment.
  3. Assign the path follower with conservative speed and no nearby traffic.
  4. Tune steering and speed following.
  5. Add traffic gap and lead-vehicle behavior.
  6. Add obstacle sensors and avoidance.
  7. Test stuck detection, reverse recovery, and reset.
  8. Introduce zones and more aggressive behavior last.
Traffic policy controls spacing intent, not guaranteed collision avoidance. Time gap and minimum gap must suit speed and braking capability. Sensors have limited range and geometry. A heavy truck needs earlier braking and wider route geometry than a lightweight race car even when both use the same path component type.
Do not tune AI only at one frame rate or with one vehicle. Update timing, physics step, path complexity, and vehicle capability can expose different behavior under load.
Damage, wheel health, and recovery
Wheel health converts configured damage into staged physical and visual consequences. Damage intensity, thresholds, rim/tire setup, tire explosion presentation, audio, and performance effects must agree. Test damage with a repeatable impact or sustained burnout, then observe health reduction, stage transitions, tire or rim visuals, ground sound changes, wheel behavior, and UI feedback.
Damage and repair zonesPro
Vehicle Damage Zones and repair zones require MVC Pro. The underlying wheel-health system and non-zone damage tests remain Community compatible.
A damage zone provides a repeatable trigger, while a repair zone restores supported state according to its mode. A repair zone should not conceal a wheel hierarchy that was invalid before damage occurred. If visuals recover but handling does not, inspect the runtime wheel state rather than repeatedly re-entering the zone.
Vehicle reset
Vehicle reset is a different recovery mechanism. It detects a flipped or unusable vehicle, relocates it to a stable state, and controls collision re-enablement through configured timeouts. Keep reset cooldown long enough to prevent the restored vehicle from immediately intersecting traffic or scenery.
Community and Pro availability
Badge placement defines its scope. A Pro badge in a section header marks the complete section or tutorial as an MVC Pro workflow. A Pro callout beneath a subsection heading marks only the specifically named field, component, or step that follows it; the surrounding unmarked workflow remains available in Community unless another note says otherwise.
Mixed systems deliberately keep their shared foundation unbadged. Examples include Unity Wheel Collider physics, the default tire and ground presets, static exterior lights, wheel health, wheel marks, and ordinary chassis setup. Their external integrations, multiple-preset tools, dynamic or interior light features, advanced chassis controls, and other guarded additions carry local Pro callouts at the point where the workflow changes.
A Pro marker describes the installed package surface, not whether a specific project has enabled the feature. An unmarked control can still be hidden when its parent system is disabled. A Pro control can still be unavailable when the Pro package has not compiled or the license state is unresolved.
When a field shown in this manual is absent, check the manual version, MVC package version, edition, active physics integration, parent feature toggles, and inspector diagnostics. Do not add a hidden internal component to imitate a missing licensed workflow.
Production workflows
A vehicle that drives in an isolated scene is a prototype. A production vehicle must also survive prefab changes, scene loads, input switching, quality tiers, save data, pooling, upgrades, and repeatable testing. This chapter turns the component reference into maintainable project workflows.
The recommendations below separate MVC package content from project-owned content, establish clear ownership for global and scene services, and make tuning reproducible. Adapt the architecture to the game, but write down every deliberate exception. Consistency is more valuable than a clever hierarchy that only one developer understands.
Project architecture and ownership
Divide the project into three ownership areas. Package-owned MVC files are installed, repaired, and upgraded as a unit. Project-owned vehicle content contains models, prefabs, presets, audio, effects, materials, configuration exports, and integration scripts. Scene-owned content contains the manager, followers, UI, ground mapping, paths, and zones required by a particular level. This separation answers where a change belongs and what can be replaced safely.
Package-owned content
Treat package scripts, editor code, samples, and default resources as upstream. Do not make routine vehicle tuning by editing these files. When a package change is genuinely necessary, document the exact reason, keep a patch or project-owned extension, and expect to re-evaluate it on every upgrade. A repaired installation can restore upstream files and remove undocumented edits.
Project-owned content
Create stable folders for vehicle prefabs, MVC presets, configuration exports, audio libraries, VFX, materials, UI, drivers, paths, and integration code. Copy sample assets into these folders only when their license and intended use permit it, then rename and maintain them as project content. Avoid placing project-owned scripts or data inside a package directory merely because the related MVC file is nearby.
Scene-owned content
Decide whether Vehicle Manager, Vehicle Follower, UI Controller, and environmental mapping are created by a bootstrap scene, owned by each gameplay scene, or persisted across scene loads. Do not let different levels make that decision accidentally. A persistent service needs duplicate protection and a clear reset policy. A scene-local service needs every scene to include and configure it consistently.
Naming rules
Use names that express role and scope: `Vehicle_Player_Sport`, `Engine_V8_Street`, `Tire_Sport_Dry`, `Ground_Asphalt_Dry`, `Camera_Chase_Close`, or `Path_Traffic_Clockwise`. Avoid several assets named `Default`, `New Preset`, or `Copy`. Display names can be friendly, but asset names should make assignments and version-control diffs understandable without opening Unity.
Assembly boundaries
Keep integration scripts in project-owned assemblies with deliberate references to MVC and any optional Unity packages. Separate editor-only helpers from runtime assemblies. This prevents editor namespaces from entering builds, clarifies dependency direction, and makes optional integrations removable. When a compiler error appears after an upgrade, the assembly boundary also reveals whether the failing code belongs to MVC, an integration, or game logic.
Vehicle prefab authoring
Build one authoritative prefab per production vehicle or per meaningful base configuration. The prefab should open in isolation with a readable hierarchy, valid MVC diagnostics, deliberate component references, and no scene-object dependencies unless the architecture injects them at runtime. A scene instance is a test or placement of that prefab, not the only location where important tuning exists.
Establish scale before physics
Correct import scale before configuring wheel radius, suspension, mass, camera distance, driver pose, hitch location, and effect size. Prefer a clean root scale and predictable child transforms. Rescaling a finished vehicle changes the spatial meaning of most authored data and forces a complete physics and presentation retest.
Use a stable hierarchy
Keep the Vehicle root stable. Place the physical chassis and body colliders under a clear chassis branch. Group non-rotating brake objects separately from rotating rim and tire meshes. Give each wheel an unambiguous side and axle name. Group exhausts, lights, camera pivots, driver targets, and trailer links by role. Avoid numeric names such as `Wheel (1)` after the model reaches production.
Prefer narrow prefab variants
Use a prefab variant when several vehicles genuinely share a maintained base, such as a fleet using the same physical platform. Do not use inheritance only to avoid duplicating a few obvious values; deep variants can hide overrides and make an upstream change affect unexpected vehicles. Review overrides before applying them to the base and test every dependent variant after a shared change.
Control scene overrides
A scene instance can temporarily override values during testing, but accepted tuning should return to the prefab or assigned preset. Before committing a scene, inspect its overrides. Unexplained changes to mass, wheel role, engine, tire, input, or diagnostics often indicate that a test value was never promoted to the authoritative asset.
Use configuration exports as checkpoints
Export a vehicle configuration before a risky tuning pass, import operation, or migration. Name the file with the vehicle, purpose, MVC version, and date or revision. A configuration export supports comparison and recovery of MVC data, but the prefab and source-control history remain authoritative because referenced models, materials, audio, effects, scripts, and scene services are outside the export.
Prefab completion gate
  • The model uses the intended real-world scale and root orientation.
  • The Vehicle root has a stable name, Rigidbody relationship, and body collision.
  • Every wheel has a clear axle, side, steering, driven, and braking role.
  • Required presets are assigned and no duplicate asset with the same display name is mistaken for the intended one.
  • Optional modules are either configured completely or disabled deliberately.
  • Diagnostic errors are resolved and warnings are reviewed.
  • The prefab drives correctly in a minimal validation scene without production-scene dependencies.
Preset and tuning discipline
A preset should capture one reusable intent. An engine preset describes a power source; it should not silently compensate for a bad transmission. A tire compound describes contact behavior; it should not be tuned only to hide an incorrect center of mass. A camera preset describes a view; it should not depend on one vehicle's accidentally oversized bounds. Keep responsibility narrow enough that a preset can be understood and reused.
Start from a named baseline
Before tuning, duplicate or export the current known-good preset and identify the test goal. Record the scene, vehicle mass, ground, weather or wetness, input method, physics integration, Unity fixed timestep, and camera. If any of those change during the experiment, it is no longer a controlled comparison.
Change one relationship
A relationship can include several values that must remain coherent, such as an RPM range, a set of gear ratios, front and rear spring balance, or both axes of a friction curve. Change that relationship, repeat the test, and write down the result. Avoid changing engine power, tires, steering, assists, and camera shake in the same pass because no observation can identify the cause.
Record real-world sources
When recreating a real vehicle, record the specification source, market or trim, unit, and conversion. Manufacturer, catalog, and test values can disagree because they describe different variants or conditions. Treat source numbers as inputs to a simulation model, not a guarantee that the complete vehicle will reproduce a published result without matching tires, gearing, aerodynamics, mass, and test conditions.
Name experiments honestly
Use suffixes such as `_Baseline`, `_Arcade`, `_Wet`, `_Drift`, `_Heavy`, or `_Experimental` while comparing. Do not rename an unverified experiment to `Final`. Once accepted, move or delete obsolete candidates according to project policy and update assignments explicitly. A long list of indistinguishable presets makes later troubleshooting slower than repeating the original tuning.
Validate assignment, not only content
After editing a preset, confirm the tested vehicle references that exact asset. Duplicate names, sample copies, runtime clones, and prefab overrides can make a correct edit appear ineffective. Exit and re-enter Play Mode when initialization copies preset data. Test a second consumer before declaring a shared preset safe.
Build a vehicle validation scene
Create a small scene dedicated to repeatable vehicle tests. It should load quickly, contain no unrelated gameplay, and remain stable across releases. The scene is not a showcase environment; it is an instrument that reveals changes in initialization, physics, input, surfaces, sound, effects, cameras, and performance.
Recommended test areas
  • A flat launch lane with visible distance markers for acceleration and shift comparison.
  • A braking lane with a fixed entry marker and enough runoff to compare cold and heated brakes.
  • A constant-radius circle or skidpad for steady steering and tire balance.
  • A slalom with consistent spacing for steering response, weight transfer, and recovery.
  • A bank, crest, dip, ramp, and uneven section for suspension travel and contact.
  • A low curb, seam, and narrow obstacle for wheel radius and collision behavior.
  • Mapped asphalt, dirt, grass, gravel, sand, and wet variants used by the project.
  • A tunnel or garage for spatial audio and reverb transitions.
  • A dark area and weather zone for exterior and interior lighting.
  • A simple AI loop and traffic route that do not depend on production navigation.
  • A trailer staging area with flat attachment alignment and room to reverse.
Fixed start states
Place named spawn transforms for every test. Reset vehicle pose, linear and angular velocity, gear, engine state, energy, health, tire state, and active assists before each measurement. Use the same input sequence where automation is available, or document the manual sequence. A comparison that begins from a different speed or surface is not evidence of a tuning change.
Useful observations
Record time or speed at fixed distance markers, shift RPM, stopping point, maximum or steady steering response, wheel contact loss, suspension travel, intervention state, surface identity, energy consumed, and frame-time impact. The goal is not to collect every possible number; it is to capture enough evidence to determine whether a change improved its intended behavior without breaking another system.
Preserve the scene
Keep the validation scene and its project-owned assets under source control. Avoid replacing its geometry or ground presets casually because that destroys historical comparison. If the test scene must evolve, record the revision and establish a new baseline for representative vehicles.
Integrate a gameplay scene
Integrate systems in dependency order. Begin with the active MVC settings and a compiling project. Add scene-level ownership, one known vehicle, physical ground, and input. Then add follower camera and UI. Add mapped surfaces, audio, VFX, damage, lighting, AI, zones, and traffic only after the simpler scene remains valid.

Additive loading
When scenes load additively, references can become valid at different times. Establish a bootstrap or registration step that makes ownership explicit. Do not rely on a manager finding whichever object happens to awaken first. Before unloading a scene, remove or redirect vehicles, paths, ground mappings, and zones that depend on it.
Scene duplication check
Search the loaded hierarchy for duplicate managers, followers, listeners, EventSystems, and player UI. Some duplicates produce immediate warnings; others appear to work while alternating ownership from frame to frame. Validate the final loaded scene combination, not only each scene opened separately in the Editor.
Environmental boundaries
Test where systems meet: Terrain to road mesh, one mapped surface to another, light to darkness zone, dry to wet area, path to intersection, reverb zone entry, and additive scene seam. Boundaries expose overlapping colliders, missing mapping, abrupt presentation, and stale ownership more reliably than driving in the middle of a large uniform area.
Multiple vehicles and player switching
Vehicle switching is a coordinated ownership change. Input, camera, UI, audio emphasis, mobile preset, gamepad selection, and gameplay code should agree on the same active vehicle. Updating only Vehicle Manager while a custom UI script retains the previous instance produces a partial switch that is difficult to diagnose.
  1. Confirm the destination vehicle is initialized, active, and eligible for player control.
  2. Release AI or other control ownership according to the game rules.
  3. Change the active vehicle through the manager workflow.
  4. Confirm player input and selected device now affect the destination.
  5. Confirm the follower target and vehicle-specific camera pivots update.
  6. Confirm UI, audio focus, interaction prompts, and custom gameplay scripts update.
  7. Assign the old vehicle its new state: idle, AI-controlled, parked, pooled, or destroyed.
Do not infer readiness from visibility
A visible vehicle may still be mid-initialization, missing energy, held by brakes, controlled by AI, or absent from the manager's registered list. Gate switching on an explicit ready state. When a switch is requested during scene loading or pooling, queue or reject it deliberately rather than leaving half the services on each vehicle.
Device ownership
For local multiplayer or alternate control devices, define which player owns each device and manager context. Test device disconnect and reconnect, controller order changes, keyboard sharing policy, pause, and focus loss. Do not assume the first enumerated gamepad remains the intended one across platforms or sessions.
Split-screen considerations
Each viewport normally needs deliberate camera, listener, UI, and input ownership. Audio-listener policy and global presentation effects require game-specific decisions. Validate VFX culling and Wheel Spin visibility against the intended cameras; an optimization using one active camera can behave differently when several views exist.
Runtime spawning and pooling
Spawn a complete configured prefab whenever possible. If dependencies must be injected, keep the object inactive until the required presets, scene services, and gameplay data are assigned, then activate it through one controlled initialization path. A vehicle should not spend several frames active while wheels, drivetrain, or manager ownership are still missing.
Spawn validation
  • The spawn pose is above a valid surface with enough suspension clearance.
  • Body and wheel colliders do not overlap other spawned objects.
  • The manager registers the new Vehicle exactly once.
  • Input or AI ownership is assigned intentionally.
  • Follower and UI change only if the new object should become the player vehicle.
  • Runtime-created audio, native data, effects, and diagnostic state initialize without Console errors.
Pool reset contract
Define what returns to baseline when a pooled vehicle is released: position, velocities, sleeping state, engine, RPM, gear, clutch, fuel or battery, health, wheel damage, brake heat, inputs, lights, indicators, audio, particles, marks, AI behavior, path progress, target, trailer links, driver state, camera pivots, and UI selection. Some games intentionally preserve wear or energy; that exception belongs in the pool contract.
Unregister before reuse
Disable or release the vehicle through the expected lifecycle so manager lists, UI, followers, AI, and custom registries remove it. Do not teleport an object into the pool while services still consider it active. Before reuse, verify no event subscription, coroutine, async operation, or project script retains state from the previous owner.
Spawn under load
Test spawning during traffic, after additive scene loads, at low frame rate, and near scene boundaries. Performance spikes can change when registration and initialization occur, but simulation correctness should not depend on frame timing. If many vehicles enter together, stage activation according to a documented policy and profile the result.
Save and load vehicle state
Separate configuration from mutable gameplay state. Configuration identifies which vehicle prefab and presets define the vehicle. Mutable state includes transform, velocity, fuel or battery, health, wheel condition, selected gear, lights, attachments, and game-specific upgrades. Saving every serialized Unity field produces fragile data tied to internal implementation details.
Choose intentional fields
Write a project-owned save schema with stable identifiers for vehicle type and reusable assets. Store only state the player expects to persist. A race restart may preserve configuration but reset damage and energy. An open-world garage may preserve upgrades, cosmetic choices, fuel, and wear but intentionally restore a safe pose.
Load in phases
  1. Read and validate save version and stable identifiers.
  2. Spawn or obtain the correct configured prefab while inactive.
  3. Apply supported project configuration or upgrades.
  4. Initialize MVC and required scene ownership in the documented order.
  5. Apply mutable health, energy, cosmetic, and gameplay state at the correct lifecycle point.
  6. Place the vehicle at a validated pose and restore velocity only when safe.
  7. Restore attachments, active-player ownership, camera, and UI after every referenced object exists.
Version the schema
Package and project upgrades can rename presets, change available features, or alter valid ranges. Include a save-schema version and write explicit migrations. When an old identifier no longer exists, choose a documented fallback and report it rather than silently loading a random first preset.
Do not use configuration export as a save file
MVC vehicle configuration export supports authoring portability and checkpoints. A game save needs project identity, security, versioning, player ownership, world state, and intentionally mutable data. Use the API reference and project adapters to read or apply the state required by the game instead of exposing an editor-oriented export directly to players.
Platform and build validation
Create a support matrix before production tuning hardens around one workstation. Record Unity version, target platforms, render pipeline and quality tiers, physics integration, input backend, control devices, audio output expectations, vehicle count, camera count, and required MVC edition features. Every row needs an owner and a test build.

Player comfort and accessibility
Vehicle feel includes how information and motion reach the player. Provide configurable control bindings, sensitivity, inversion, dead zones, camera motion, vibration, audio balance, and interface scale according to the game's accessibility goals. MVC exposes the vehicle state and several presentation controls; the game owns the player-facing settings experience and persistence.
Camera comfort
Offer control over shake and strong pulses when they are not essential to gameplay. Avoid stacking engine, speed, skid, collision, and environmental shake at full intensity. Check low field of view, high field of view, interior views, and sustained reversing. Test with frame-rate variation because unstable presentation can amplify discomfort.
Input flexibility
Support rebinding where the project input architecture allows it. Treat steering and pedals as ranges when appropriate, provide keyboard alternatives, and let players tune sensitivity and dead zones without invalidating the physical setup. Mobile layouts should respect safe areas, different hand sizes, left- or right-handed needs where supported, and the ability to choose buttons, joystick, or sensor steering.
Information should not rely on one channel
Do not communicate critical engine, damage, assistance, or navigation state only through color, sound, vibration, or a tiny icon. Combine channels according to the game: labeled status, distinct shapes, readable contrast, optional captions, and adjustable audio groups. Verify status sprites in their normal, active, and unavailable states against every background they can cover.
Assist behavior
If the game exposes ABS, TCS, stability, automatic transmission, reset, camera assistance, or simplified controls as player options, define what each option changes and retain a recoverable default. Accessibility assists should operate on a mechanically valid baseline. A hidden correction that constantly fights bad tire or steering data becomes inconsistent and difficult for players to learn.
Regression test matrix
Maintain a small set of representative vehicles rather than attempting every test on every model. Include the lightest and heaviest body, shortest and longest wheelbase, fastest vehicle, manual and automatic transmission, combustion and electric power, front/rear/all-wheel drive used by the game, a trailer combination, an AI vehicle, and a vehicle with the most complex presentation.
Core test pass
  • Cold scene load produces no MVC error or missing reference.
  • Engine or motor starts according to policy and responds to throttle.
  • Forward, neutral, reverse, clutch, and gear changes behave as configured.
  • Steering returns correctly and remains controllable at low and high speed.
  • Cold and repeated braking are stable; parking brake releases.
  • All wheels report plausible contact, suspension, slip, and visual alignment.
  • Reset restores a usable pose and clears the intended transient state.
  • Fuel or battery, damage, tire health, and brake heat change only when enabled.
Presentation pass
  • Engine, ground, impact, exhaust, charger, and transmission audio route correctly.
  • Ground particles and wheel marks follow the resolved surface.
  • Exhaust, damage, brake heat, lights, and wheel spin trigger and cull correctly.
  • Every camera preset frames the vehicle, handles obstacles, and switches cleanly.
  • UI values follow the selected vehicle and status indicators use the correct state.
  • Driver IK stays aligned through steering, camera changes, and vehicle movement.
World and lifecycle pass
  • Ground boundaries, Terrain layers, wetness, weather, damage, lighting, and reverb zones transition deliberately.
  • AI follows paths, maintains spacing, detects obstacles, reacts to zones, and recovers.
  • Trailers attach, turn, brake, reverse, chain, detach, and clean up.
  • Vehicle switching transfers input, camera, UI, and gameplay ownership.
  • Spawn, pool, disable, destroy, scene unload, pause, and resume leave no stale references.
  • The same representative pass succeeds in a target-platform build.
Failure reporting
Record the matrix row, project revision, MVC version, scene, vehicle, platform, reproduction steps, expected result, actual result, frequency, first Console message, and evidence. Link the failing result to a known passing build when possible. Reopen a fixed issue only when the same acceptance condition fails; file a separate issue when the visible symptom has a different cause.
Safe custom integrations
Game-specific code should integrate with MVC through documented public behavior while remaining owned by the project. The goal is not to prevent customization; it is to keep the boundary visible so an MVC repair or upgrade does not overwrite game logic and a game-system change does not require modifying controller internals.
Write the contract first
Describe what the integration reads, what it writes, when it runs, and which object owns it. For example, a garage upgrade adapter may select an engine and tire preset before Vehicle initialization, while a dashboard adapter may read speed and RPM after initialization without changing physics. A replay adapter may record intentional inputs and state, while a damage-gameplay adapter may request health changes through supported members. These contracts have different lifecycle and authority requirements.
Prefer an adapter component
Place a small project-owned MonoBehaviour beside the game system or vehicle it adapts. Give it explicit serialized references or inject them through the project bootstrap. Avoid global object searches on every frame and avoid private reflection into MVC implementation. The adapter should fail with a clear validation message when a required reference is absent instead of silently finding an arbitrary object with a familiar name.
Read state at the appropriate rate
Not every consumer needs physics-rate data. A UI text label can update at a presentation rate; a physics assist or force integration belongs in the appropriate fixed simulation phase; an audio or animation parameter may update each rendered frame but should use stable MVC state. Choose the rate from the consumer's requirement and profile it. Do not add twenty scripts that each rediscover the active Vehicle and calculate the same derived value every frame.
Use events deliberately
Events are appropriate for discrete transitions such as vehicle selection, engine start, gear change, health failure, or attachment when the relevant public API exposes them. Subscribe and unsubscribe with the object's lifecycle, especially for pooled vehicles and persistent UI. Poll continuously changing values such as speed only when needed and at a suitable frequency. An event subscription that survives object destruction can keep stale vehicles alive or update the wrong interface after switching.
Do not mutate shared presets accidentally
A runtime change to a shared ScriptableObject or preset can affect every consumer in the session and can sometimes appear as an editor asset modification. Decide whether an upgrade selects another project-owned preset, creates a runtime copy, or changes one vehicle's supported runtime state. Document how the change resets when leaving Play Mode, pooling the vehicle, loading a save, or returning to a garage.
Input adapters
A custom input adapter should produce the same semantic actions expected by the Vehicle: normalized steering and pedal ranges, discrete gear or feature actions, release behavior, and player ownership. Apply dead zones, sensitivity, device pairing, and rebinding in one clear layer. Test lost focus, disconnected devices, mobile multi-touch, and a switch from player to AI control. Never leave the last non-zero throttle or steering value latched when the input source is disabled.
UI and telemetry adapters
Keep presentation calculations out of the vehicle configuration. Convert units, format text, animate custom gauges, and choose warning thresholds in a UI adapter or view model that reads the currently selected Vehicle. Cache references but refresh them on vehicle switching. When a UI value appears wrong, compare the raw MVC state, unit conversion, formatting, and animation separately.
Gameplay assists
Project assists such as automatic recovery, route guidance, stunt scoring, accessibility steering, or simplified braking should state whether they modify input, request an MVC feature, or apply an external physical effect. Test them with built-in ABS, TCS, stability, counter-steer, and AI behaviors so two systems do not correct the same condition in opposite directions. Expose diagnostics that identify when the project assist intervenes.
Networking boundary
A networking adapter must follow the chosen framework's authority, prediction, reconciliation, interpolation, and ownership model. Decide which peer simulates physics, which inputs are transmitted, which state is corrected, and how remote presentation is smoothed. Do not synchronize every serialized MVC field every frame. Send the smallest intentional state required by the game and validate switching, late join, despawn, trailer links, damage, and scene transitions under latency and packet loss.
Optional package boundary
Wrap integrations for optional Unity or third-party packages behind their own assembly definitions and compile conditions according to project policy. Removing an optional package should disable only its adapter, not break the core vehicle assembly. Keep editor utilities in an Editor assembly and runtime code free of UnityEditor references so player builds do not depend on editor-only APIs.
Upgrade proofing
Record every MVC public type and member used by project code. Before upgrading, compile adapters against the new version, read affected release notes, and run focused tests for each contract. A compile success proves only that names and signatures remain available; runtime timing, units, initialization, supported ranges, and ownership still need validation.
Integration acceptance checklist
  • The integration lives outside package-owned folders and has an identified owner.
  • Required MVC edition, public API, Unity package, and assembly references are documented.
  • Initialization order and failure behavior are deterministic.
  • Vehicle switching, disable, destroy, pooling, scene reload, and application quit clean up references and subscriptions.
  • Shared presets are not mutated unintentionally.
  • The integration has a minimal test scene or automated test and a documented expected result.
  • Its performance cost is measured at representative object counts.
  • Upgrade tests cover behavior as well as compilation.
Team handoff and change review
Vehicle work crosses design, programming, art, audio, VFX, animation, UI, and QA. Define which assets each discipline owns and which tests must pass before a change moves downstream. A perfectly tuned Rigidbody can be invalidated by a model rescale; a correct audio preset can fail after folder reorganization; a camera can change perceived handling without touching physics.
Designer handoff
Provide the authoritative prefab, assigned presets, validation scene, intended handling description, baseline measurements, control mode, and allowed tuning scope. Identify shared presets whose changes affect several vehicles. Designers should export or branch experiments rather than overwriting the only known-good setup, and record the maneuver used to accept a change.
Vehicle artist handoff
Specify import scale, forward and up axes, body origin, wheel centers, wheel radius, rotating and non-rotating parts, brake and caliper structure, lights, emissive material slots, exhaust origins, interior controls, driver seat, camera-safe cockpit geometry, damage meshes, and trailer pivots. Renaming or restructuring assigned transforms is an integration change, not a cosmetic-only edit.
Technical art and VFX handoff
Record render pipeline, supported quality tiers, shader properties used for emission or damage, transparent-material requirements, particle orientation, bounds, scale, ground dependencies, mark materials, culling expectations, and target-camera size. Test effects from the player camera and in a build. An effect that exists only in Scene view is not complete.
Audio handoff
Document clip ownership and license, sample preparation, Resources folder path, engine filename and RPM convention, acceleration and deceleration folder policy, mixer routing, spatial settings, event trigger, and loudness baseline. Audio should be auditioned in the complete mix and by category. Moving an engine folder or changing its naming scheme requires a runtime-loading test.
Animation and driver handoff

Validate the pose across the complete steering range and after prefab instantiation, not only in edit-time preview.
UI and input handoff

Supply a test sequence that activates every indicator and reaches needle endpoints. Do not approve a dashboard from a static display state; validate it while the vehicle is running.
Programming handoff

QA handoff

Setup & Create a Vehicle
Configure a clean MVC project and turn a prepared four-wheel model into a controllable vehicle.
Tutorial: 01 of 20
Goal: Configure a clean MVC project and turn a prepared four-wheel model into a controllable vehicle.
Prerequisites: Unity 2022.3.62f3 or a compatible supported editor, the installed MVC package, a vehicle model with separate wheel objects, and a test scene with a drivable surface.
Expected result: A tested configuration that can be reused or compared against a known baseline.
By the end of this tutorial, the imported model will be a fully controllable vehicle. The workflow configures the project, creates the MVC object, connects essential components, and finishes with a clean Play Mode test.
The core vehicle-creation workflow uses the free MVC Community edition. Optional MVC Pro collider controls, mapped-surface authoring, and chassis response are marked only at the steps where they apply.
Understand the project workflow
This tutorial will give you a practical guide to setting up a drivable car in Unity.
For a detailed explanation, always refer to the Manual and API documentation in the related reference sections.
Start by import the MVC package from Unity Package Manager, which can be accessed from the Window menu, Package Management, then Package Manager.
Import MVC from Package Manager
Inside the Package Manager, click on the "My Assets" tab and search for the Multiversal Vehicle Controller package you got from the Unity Asset Store.
Click on the package and import it into your project.
Open the Setup Wizard
The MVC normally opens its Setup Wizard when the project needs configuration. If it does not appear, open the Tools menu, Multiversal Vehicle Controller, and choose Install/Repair. This is also the menu to revisit when project settings or package files need to be checked.
Configure project-wide settings
When the Setup Wizard opens, click "Let's get started". Accept the recommended settings with "Yes". Review every requested project change, click "Continue" to apply it, and close the success message with "Okay".
After installation, configure MVC. This example uses HDRP and Unity Wheel Collider, which the Setup Wizard establishes as the built-in physics baseline.
MVC Pro can use imported custom wheel-physics integrations. The optional [#custom-wheel-colliders](Pacejka Wheel Collider guide) covers the ready-made BxB Studio integration, but complete this first vehicle with Unity Wheel Collider so later backend comparisons start from a known result.
Set gameplay and editor units to Metric for this example and select Inputs Manager. A project that already depends on Unity's Legacy Input Manager can select that backend instead, but should not mix bindings unintentionally.
For the project layers, Vehicles is used for complete vehicles, and Vehicle Wheels is used for their wheels. These two layers must be different, and neither should be left on Default, because the MVC uses this distinction when filtering vehicle and wheel interactions. The "Assign Recommended Layers" button can help you do this easily, so you can try it out.
Then the final required field is the MVC audio folder path. It must live inside a Resources folder. Here it is configured as Resources/Audio. If you choose another folder, make sure to keep it under a Resources folder so audio clips can be loaded at runtime.
Finish installation and import sample assets
Next, click "Start install" and click "Yes" to confirm the settings.
The wizard may offer to import the complete Getting Started Demo. Select "No" when following this tutorial, because the required files are imported selectively in a later step.
Wait for the Setup Wizard and Unity Package Manager to finish importing and compiling before interacting with the project.
Once setup is complete, open the Settings Panel. General contains project-wide behavior; Player Inputs contains control mappings; Engines and Chargers stores drivetrain presets; Tire Compounds and Grounds control contact behavior; SFX and VFX control presentation; and Cameras stores reusable camera presets. Later tutorials return to each area in context.
Close the panel and import only the required Getting Started Demo assets from `Tools > Multiversal Vehicle Controller > Samples > Getting Started Demo`.
You might be prompted to import the Text Mesh Pro Essential assets; click "Import".
When the package import window opens, select the assets required by the project and click "Import".
Review the import list before accepting it. Do not overwrite the project's MVC Settings Data asset with a sample configuration unless replacing the current project settings is intentional and backed up.
If you're using HDRP or URP for your project, you might be presented with an additional package to import. If that's the case, select these assets, then click "Import" one last time.
Prepare the vehicle model
A project without the Demo package can report missing optional VFX assets. Disable unused VFX modules until project-owned effects are ready rather than assigning arbitrary placeholders.
With project setup complete, prepare the first vehicle model.
Use a vehicle model whose body, wheel meshes, and moving parts can be organized independently. Verify its license and import scale before bringing it into the project.
Import the model and place it in the scene at real-world scale. Before adding MVC components, organize its hierarchy so moving and rotating parts can be assigned reliably.
The vehicle hierarchy needs to be composed of the following: a Chassis holding body objects, a Wheel Brakes GameObject for objects that follow the wheels but don't rotate, such as brake callipers, and finally a Wheel Transforms GameObject containing the wheels.
Each wheel should have Rim and Tire GameObjects. Having separate parts of the wheel will allow the MVC to simulate tire wear better. Additionally, you can add a brake disc per wheel, which can be found in the assets of the Getting Started Demo that we imported.
You can use a free tool like Blender to modify the car model to your liking.
In the configured example, we have two variants per disc; the normal variant is for the right wheels, while the flipped variant is for the left wheels.
You can also find a couple of brake calliper models available inside the Demo package.
Create the MVC vehicle
Create MVC components from either `GameObject > MVC` or `Tools > Multiversal Vehicle Controller > New`; both commands use the same creation workflow. Select the model root and add a Vehicle.
When adding Vehicle to a prefab instance, Unity or MVC can request permission to modify or unpack the instance. Preserve the original prefab and continue only when these structural changes belong to the intended vehicle prefab.
Follow the Vehicle Inspector diagnostics from top to bottom. Red errors block a valid configuration; warnings normally identify incomplete references or recommended improvements. Open the Components tab and add the Chassis first.
Use the add action in the Chassis section. If MVC offers to rearrange the model, accept only when the hierarchy has not already been organized. For a prepared hierarchy, choose `No thanks` and keep the explicit structure.
Add four wheel slots for a four-wheel car, assign the physical wheel transforms in axle order, and click `Generate Wheels`. Answer the steering and powertrain prompts according to the real vehicle layout.
Allow automatic assignment of rim, tire, brake disc, and caliper objects when their hierarchy and names are unambiguous. Otherwise, decline and assign each reference manually, comparing left and right wheels carefully.
Next, you will choose the powertrain and steering setup. Basically, how the MVC works in this case is that it detects the local position of each wheel relative to the root transform and determines the front and rear wheels automatically. So, you will choose "AWD" or All-Wheel Drive for the powertrain and "FWD" or Front-Wheel Drive for steering.
Now, if we open the wheel sections, you'll see that objects, settings, and dimensions have been assigned automatically based on the information you have provided for the tool.
Add body collision and physical references
The vehicle requires deliberate body collision. Missing, overlapping, or badly scaled body colliders can produce unstable contact, terrain penetration, and unrealistic impacts.
Before the first Play Mode test, add a Vehicle Follower and Vehicle Manager to the scene. Creating them explicitly preserves the intended camera and player-selection settings instead of relying on temporary defaults.
So, to add a Vehicle Follower, go to the Tools menu, Multiversal Vehicle Controller, New, Follower. Notice that if you already have a camera in your scene, it will be automatically moved inside the created GameObject, and the Audio Listener will be moved to the Follower root GameObject.
The camera exposes several tuning fields. Begin with Dimensions, which controls the camera height and distance.
Create Vehicle Manager from the same `New` menu by selecting `Manager`. It tracks vehicles in the scene, identifies the player vehicle, and coordinates the input device assigned to that player.
You can assign a specific player vehicle manually through the Target field.
You can also control time and weather conditions that affect lights, which you will explore in later tutorials.
Use the Vehicle Profiler
The MVC also includes a Vehicle Profiler, accessible from the Tools menu!
In Edit Mode, it exposes specifications and dimensions. In Play Mode, it can display Rigidbody data, vehicle statistics, inputs, lights, and wheel telemetry.
This is one of the fastest ways to inspect what the controller believes is happening without filling your screen with temporary debug scripts.
Refine body colliders
A simple Box Collider is sufficient for an initial test, but a coarse body shape can catch on uneven terrain or steep transitions.
Use Anti-Ground CollidersPro
Anti-Ground Colliders and collider-ignore controls require MVC Pro. Community vehicles should use a clean compound body collider that avoids unwanted road contact.
The anti-ground collider system lets us select body colliders that should ignore configured ground surfaces.
This system requires that each part of the body has its own collider, which can use separate box, sphere, or capsule colliders per part, but for the sake of demonstration you will add mesh colliders.
You can also notice that we have added a separate collider to the roof to prevent it from clipping through the ground in case the car is flipped upside down.
Then, we head to our Vehicle, open the Components tab, click the Anti-Ground Colliders edit button, and supply the list of colliders we don't want the ground to collide with.
Map multiple scene surfacesPro
Ground Mapper and multiple named surface assignments require MVC Pro. Community uses the configured default ground preset.
Next, define the surfaces that MVC can contact. Add a Ground Mapper to every relevant surface, such as terrain and road meshes.
Use the Ground Surface Mapping tutorial when the scene requires several named surfaces, Terrain-layer mapping, or surface-specific presentation.
Enter Play Mode and drive across the test area. The vehicle should remain on mapped, drivable surfaces, reject slopes beyond the configured limit, and navigate without unexpected contact loss.
Add exhaust and chassis response
Next, move on to some detailing features: exhaust movement and chassis torque.
Configure chassis torque responsePro
Engine-torque chassis response and its effect multiplier require MVC Pro.
The chassis torque allows the car body to respond to engine torque. This is mostly apparent in real life on old muscle cars with huge superchargers, but you will show it in this tutorial for demonstration.
Open the Chassis Engine tab and click its edit action to expose engine-position and torque-response settings.
The main ones control the engine position, split into two parameters: position and offset. For this car, we can choose mid-rear or rear as they're the same in terms of behaviour, since the engine is located between the driver's seat and the rear wheel axle.
Then we can move the offset to determine exactly where the engine is located, either using the offset slider or using this purple sphere in the scene view.
Chassis torque provides three modes. `Off` prevents engine torque from influencing the chassis. `Auto` applies the effect only in qualifying states. `Always-On` applies it whenever engine torque is available. Establish the engine position before comparing modes.
And the last parameter is the engine torque effect multiplier; basically, the more we increase it, the more likely the effect is aggressive and more visible.
Configure exhaust movement
The next detailing feature is exhaust movement or rumble, which is relative to the engine RPM at runtime.
Find the exhaust mesh in the vehicle model, assign it to the Exhaust Model field, and use the Inspector preview to verify the rumble direction and scale.
You can increase the intensity of the movement or change the precision field to Advanced to control the shaking intensity on each axis independently.
A few important things to note: The exhaust and engine systems also influence other internal factors like centre of mass, dynamic audio source placement, etc., which we will discuss in later tutorials in more depth.

  • The Vehicle inspector reports valid chassis and wheel references.

Drivetrain Components
Build and validate the engine-to-wheel torque path, then compare naturally aspirated, turbocharged, and supercharged configurations.
Tutorial: 02 of 20
Goal: Build and validate the engine-to-wheel torque path, then compare naturally aspirated, turbocharged, and supercharged configurations.
Prerequisites: A valid drivable vehicle, at least one driven wheel, and access to the Engines & Chargers tab.
Expected result: A tested configuration that can be reused or compared against a known baseline.
This tutorial builds the complete vehicle drivetrain, configures an engine, records a baseline, and compares turbocharger and supercharger examples without losing the original test state.
Think of the drivetrain as a chain. The engine defines the usable RPM range and power. The transmission converts that output through its gears. The differential distributes it, and only wheels assigned to the drivetrain receive it. A charger modifies an eligible combustion engine before that power reaches the wheels.
The drivetrain workflow is available in Community and Pro.
For exact runtime behavior and public scripting members, use the related drivetrain sections in this manual and the selected API reference.
Open `Tools > Multiversal Vehicle Controller > Settings > Open Panel` and select Engines & Chargers. Engine presets are reusable data, so one preset can be assigned consistently without rebuilding the same specifications on every vehicle.
Start with the engine’s identity and fuel type, then define its mass and RPM behaviour. Minimum RPM is the lower running range. Redline is where the engine reaches its intended limit, Over-Rev describes the range beyond redline, and Maximum RPM is the absolute cap. Keep these values ordered logically so the transmission and sound system receive a sensible RPM range.
Next, enter the engine’s power and torque characteristics. These values influence acceleration, but they do not act alone. Vehicle mass, gear ratios, traction, differential behaviour, and the driven wheels all affect what reaches the road, which is covered below.
Configure the vehicle baseline
Select the vehicle, open its Performance tab, and assign the new engine. Enter values from a reliable specification for the vehicle being reproduced, then record the source and every unit conversion so the configuration remains reproducible.
Some settings are intentionally deferred because later tutorials cover them in the context where they matter. Keep the initial configuration conservative and document every real-world source value and conversion.
When a vehicle-domain term is unfamiliar, use the component and system references in this manual before selecting a value by intuition.
Run a controlled comparison
Treat the Vehicle sections as one connected system: Performance chooses the power source, Transmission converts it, Brakes oppose wheel motion, Steering and Suspension control response, and Tires determine the usable contact force.
But before changing performance, run a baseline on the same road from the same starting point. Watch launch behaviour, acceleration, RPM movement, gear changes, and the speed reached at the same marker.
After applying the new engine or drivetrain configuration, repeat that exact run. A useful comparison is controlled: change one group of values, drive the same route, and describe the behaviour you can actually see.
More power may expose wheelspin, unsuitable gearing, or stability problems that were hidden by the baseline.
Tune performance, ratios, brakes, and handling dependencies
Next, start with the Performance tab. Here, you can set the vehicle weight, override the engine specs, choose a turbo or supercharger, and adjust a couple of other related settings.
Since we have created an engine for this car, we can assign it in the Engine field, and immediately we can see the engine specs reflected, with the engine curves and performance stats changing.
You can also assign the car's top speed here, or do that manually through the next section, which is the Transmission tab.
In this section, we can find the main transmission settings, such as the gearbox type, clutch responsiveness, differentials, and gear ratios, which also determine the vehicle's theoretical top speed.
Shorter gearing usually improves acceleration but reaches its limit earlier. Taller gearing can support more speed but may make the vehicle feel slow if the engine cannot pull it.
Next, we have front and rear brake specs; these specs apply per brake, and basically all that matters in the end is the brake torque, which determines how fast a vehicle can stop.
We also have an important factor: heat threshold, which determines how fast a brake disc heats up and is determined by the brake type selection field.

Understand friction fields
Next, explain the fields we have in the inspector. "Friction Complexity" chooses how much the tire changes with speed. "Simple" uses a more direct constant-style configuration. "Complex" uses speed-dependent stiffness intervals for a more adaptable response.

Troubleshooting, maintenance, and reference
Use this chapter after completing the relevant setup or tutorial. It organizes symptoms by system, gives a repeatable diagnostic order, and finishes with upgrade guidance, frequently asked questions, terminology, and units used throughout MVC.
Most difficult vehicle-controller bugs are interaction bugs. A field can be valid by itself while the complete result is wrong because the active preset is different, a wheel is not in contact, a manager selected another vehicle, or a global feature is disabled. Diagnose from prerequisites toward presentation: compilation, settings, scene ownership, vehicle references, wheel contact, drivetrain state, and finally audio, VFX, camera, or UI.
A repeatable diagnostic workflow
Begin with a reproducible test. Record the scene, vehicle prefab, active MVC settings asset, Unity version, render pipeline, physics integration, input backend, and exact action that causes the problem. If the problem appears only after driving for a while, record the starting state and approximate time. A useful report describes what was expected, what happened instead, and whether the Console produced a warning or exception.
  1. Stop on the first compile error. Later errors can be consequences of the first one, and MVC cannot initialize reliably while the project is in an invalid scripting state.
  2. Reproduce with one known vehicle. Disable unrelated traffic, cameras, UI, weather, and gameplay scripts when they can influence the result.
  3. Confirm the active object. Inspect Vehicle Manager, the active player index, the selected vehicle, and the preset actually assigned to it.
  4. Check prerequisites. Verify the global feature toggle, required layers, tags, packages, and scene components before editing local tuning values.
  5. Observe before changing. Use the Inspector, diagnostic icons, Console, and Vehicle Profiler to identify the first state that disagrees with reality.
  6. Change one group. Save the baseline, make one focused change, and repeat the same maneuver from the same location.
  7. Return to a known configuration. If the result becomes less clear, restore the saved prefab or imported vehicle configuration rather than stacking guesses.
Evidence worth collecting
Record the complete Console message and stack trace, the vehicle hierarchy, Vehicle diagnostic panel, relevant Settings tab, wheel runtime information, and Profiler state during the failure. Include a minimal scene or configuration export when the problem survives outside the production scene. Remove license keys, store invoices, private repository URLs, usernames, and unrelated project assets from all diagnostic material and shared archives.

Vehicle does not move
Treat a stationary vehicle as a chain. Input must reach the selected Vehicle, the power source must be allowed to run, a transmission path must be engaged, driven wheels must receive torque, brakes must release, and those wheels must have usable contact and friction. Increasing engine power before finding the broken link usually hides the evidence.
  1. Confirm the vehicle is initialized and selected as the active player vehicle. If AI controls it, confirm the intended AI behavior is active instead of player input.
  2. Observe throttle and brake state. A correct keyboard or gamepad binding does not prove that the active MVC input preset is receiving it.
  3. Confirm the engine or motor is on, has fuel or battery energy when consumption is enabled, and is not stalled, disabled, or held at zero output.
  4. Inspect current gear, automatic or manual mode, neutral state, clutch engagement, and final-drive path.
  5. Confirm at least one wheel is assigned as driven and that differential assignments lead to the intended axle.
  6. Confirm parking brake and service-brake inputs are released. Inspect brake torque at each wheel if only one side resists.
  7. Confirm driven wheels report contact with a collider or Terrain and receive an appropriate tire and ground combination.
Use RPM as a clue
If throttle remains zero, investigate input or vehicle selection. If RPM never leaves the idle region despite throttle, investigate engine state, energy, and limits. If RPM rises freely while vehicle speed remains near zero, investigate clutch, neutral, ratios, driven-wheel assignment, or wheelspin. If RPM falls sharply as a gear engages, the ratio, load, brake state, or available engine torque may be unsuitable. These are diagnostic directions, not reasons to change every related value simultaneously.

Handling and stability problems
Vehicle will not steer
Confirm steering input changes, steer-capable wheels are assigned, and their pivots use the expected orientation. Inspect steering range and speed-dependent reduction. If wheels visibly turn but the vehicle continues straight, validate contact and lateral tire response. If the vehicle turns in the wrong direction, correct side, orientation, or input sign rather than compensating with unrelated chassis forces.
Persistent understeer or oversteer
Test at a repeatable speed on a known surface. Review front-to-rear tire capacity, mass distribution, steering angle, differential behavior, spring and anti-roll balance, alignment, and aerodynamic load. Understeer is not always solved by adding front grip, and oversteer is not always solved by stability intervention. Determine whether the loss occurs under power, braking, steady cornering, or lift-off because each state points to a different part of the setup.
Vehicle rolls or flips too easily
Inspect collider shape, center of mass, track width, suspension travel, spring response, tire grip, anti-roll behavior, and abrupt steering. A very high center of mass or body collider can provide enough leverage to roll even when the visual model appears low. Excessive grip can also convert sliding energy into roll. Tune the physical cause before applying a strong artificial correction.
Assistance systems appear ineffective
Create a maneuver that should activate the chosen system and observe its state. ABS needs braking near lock, TCS needs excessive driven-wheel slip, and stability behavior needs a measurable divergence or rotation to correct. If the activation condition never occurs, changing correction strength cannot help. If the system is always active, correct the baseline tire, brake, differential, or sensor configuration.
Wrong ground, tire, sound, or wheel mark
Ground-related output has two distinct questions: which ground preset was resolved, and what did the tire-ground pair produce? Diagnose them in that order. If asphalt contact resolves as gravel, changing asphalt friction or clips will have no effect because those values are never selected.
  1. Confirm physical contact and inspect the runtime ground index or name for each wheel.
  2. For a Collider, verify its mapper or mapped material points to the intended ground preset.
  3. For Terrain, inspect layer assignments, texture blending at the contact point, and the rule used when more than one layer contributes.
  4. Confirm the intended tire compound is assigned to the vehicle or wheel and that its values were not replaced by another imported preset.
  5. Return wetness to a known dry value while establishing the baseline.
  6. Test rolling, longitudinal skid, braking skid, and sideways skid separately; they can use different audio or effect slots.
  7. Inspect particles and wheel-mark materials only after the correct ground is consistently resolved.
When a boundary flickers between surfaces, inspect the physical seam and sampling point. Very narrow surface strips, overlapping colliders, noisy Terrain blends, or a wheel exactly on an edge can produce legitimate rapid changes. Adjust mapping and geometry so the desired classification is spatially stable instead of adding a large delay that makes every surface transition feel late.
Audio is missing or incorrect
First determine whether all MVC audio is silent or one category is missing. For global silence, check the active Audio Listener, MVC global volume, Unity audio settings, mixer output, pause behavior, and Console. For one category, inspect the relevant global toggle, preset, clip or folder, source, mixer group, and runtime trigger.
Engine sound
Confirm the assigned engine preset has a valid audio configuration and that its clip folder follows the configured Audio Folder Path under a Unity `Resources` directory. Review the filename splitter and RPM values encoded in filenames. Engine state and runtime RPM must change before blending can sound dynamic. If clips exist but playback is silent, inspect the generated or assigned Audio Sources, mixer routing, spatial range, and listener distance.
Ground and event sound
Ground sounds require correct surface resolution and a movement state that triggers the assigned slot. Impact, transmission, NOS, exhaust, and charger clips likewise depend on their event and feature state. Use a controlled trigger rather than waiting for an event during normal driving. If the wrong clip plays, inspect preset identity and routing before editing volume.
Reverb and spatial behavior
Confirm the zone encloses the listener or intended evaluation point, its object is active, and overlapping zones have a deliberate priority or blend. Test entry and exit slowly. A sudden change may come from a sharp zone boundary, while a change that never clears can indicate overlap or a listener that remains inside a larger zone.

Performance investigation
Measure a representative build on target hardware. Editor Play Mode includes Inspector, gizmo, domain, and development overhead that can distort conclusions. Use the Unity Profiler for frame-wide CPU, rendering, memory, audio, and physics data. MVC's Vehicle Profiler provides MVC-specific live state and vehicle behavior in both editions; neither profiler replaces the other.
  1. Establish a baseline with one vehicle in a simple scene and record frame time, fixed-update cost, rendering cost, and allocations.
  2. Add the production environment without traffic. This separates scene and rendering cost from vehicle-system cost.
  3. Add vehicles in measured groups. Record the point at which physics, AI, audio, VFX, or rendering becomes the limiting system.
  4. Disable one expensive feature group for comparison, then restore it before testing another. Keep visual quality and physics behavior changes documented.
  5. Repeat in a development build and then a non-development build on target hardware.
Common levers
Physics cost can respond to vehicle count, wheel count, collision complexity, fixed timestep, substeps, and active simulation distance. AI cost can respond to path sampling, observation scope, traffic density, and update policy. VFX cost can respond to particles, transparent overdraw, wheel marks, effect resolution, lifetime, and culling. Audio cost can respond to active sources, spatialization, effects, and voice limits. UI cost can respond to frequently rebuilt layouts and excessive per-frame text updates. Optimize the measured bottleneck and verify that the new behavior remains acceptable.
Pooling is valuable only when pooled vehicles reset completely. Reinitialize manager registration, health, fuel or battery, inputs, AI state, drivetrain, wheel state, effects, audio, UI targeting, and trailer links according to the game's rules. A fast pool that revives stale state creates intermittent bugs that are more expensive than the saved instantiation time.

  6. Let Unity finish compilation, then resolve errors from the first one forward before opening and saving production prefabs.
  7. Run the Setup Wizard or repair workflow when the release requires it, reviewing every proposed project change. Then reselect and validate any optional physics integration because the wizard can restore Unity Wheel Collider as the baseline.
  8. Open a controlled validation scene and test initialization, input, driving, braking, reverse, surfaces, audio, VFX, camera, damage, UI, AI, and trailers used by the project.
  9. Compare serialized prefabs and settings before committing the upgrade. Unexpected large changes can indicate an accidental migration or resave.
  10. Build for at least one target platform before merging. Editor-only success does not validate package stripping, Resources loading, shaders, device input, or platform settings.
Vehicle configuration import and export is a portability tool, not a complete project backup. A configuration can preserve MVC data while still depending on project assets, audio clips, materials, models, layers, and integrations. Keep source control or a full project backup as the authoritative recovery method.
Frequently asked questions
Do I need to configure every setting before a vehicle can move?
No. Start from a known preset or the vehicle creation workflow, satisfy the required chassis, wheel, drivetrain, manager, input, and ground prerequisites, and test a minimal baseline. Optional presentation and gameplay systems can be enabled incrementally.
Should I edit package scripts to tune a vehicle?
No for normal tuning. Use settings, presets, components, configuration export/import, and documented extension points. Direct package edits complicate upgrades and repairs. If custom code is required, keep it in project-owned assemblies or a deliberate integration layer.
Can one project contain Community and Pro together?
Treat them as alternative editions, not additive packages. Keep the edition intended for the project and remove duplicate installations. Pro includes the advanced surfaces, tooling, and systems identified by Pro markers in this manual.
Why does changing a preset not affect the vehicle?
The edited preset may not be the assigned instance, the feature may be globally disabled, or runtime state may have copied values during initialization. Confirm the assignment and retest from a fresh Play Mode session. Avoid editing an unreferenced duplicate with the same display name.
Can MVC values be changed at runtime?
Many runtime states and configuration values are script-accessible, but the safe timing and recalculation requirements differ by system. Use the API reference selected for this manual for the relevant public member and test changes across initialization, vehicle switching, pooling, and scene reload.
Does MVC provide networking or saved-game policy?
MVC supplies vehicle state and behavior that a game can integrate with its chosen networking and persistence architecture. Authority, prediction, reconciliation, serialization format, versioning, and anti-cheat policy belong to that architecture. Transmit or save intentional gameplay state rather than attempting to serialize every Unity component automatically.
Which render pipeline should I use?
Choose the pipeline required by the project and configure MVC visual assets for it. Core vehicle logic is separate from material compatibility, but particles, transparent wheel-spin materials, brake emission, decals or marks, and demo content must use compatible shaders.
When should I use Vehicle Profiler?
Use it while reproducing runtime behavior: verifying inputs, engine and transmission state, wheel contact, slip, speed, and other exposed vehicle data. Use the Unity Profiler when determining frame cost, allocations, rendering, physics workload, memory, or audio performance.

When recreating a real vehicle, record the source and conversion used for every specification. Before requesting support
  • The project compiles without unrelated errors.
  • The problem reproduces in the installed MVC version with the active edition identified.
  • The relevant global setting and local component are both enabled.
  • The tested vehicle, preset, input backend, physics integration, render pipeline, and Unity version are identified.
  • The first Console message and complete stack trace are preserved.
  • A minimal reproduction or configuration export is available when the issue is project-specific.
  • Sensitive license, account, path, and private-project information has been removed.
A concise report with a deterministic reproduction is more useful than a large project with unknown state. State the expected result, actual result, reproduction sequence, frequency, and the smallest change that makes the problem appear or disappear. If the issue began after an upgrade, include both versions and whether a clean installation of the current package reproduces it.
